SQL Injection Learning Notes – Understanding ' OR 1=1--

Objective

Today I focused on understanding why a SQL injection payload works instead of memorizing payloads. The lab contained a SQL Injection vulnerability in the category parameter of a product filter.

The original SQL query executed by the application was:

SELECT *
FROM products
WHERE category = 'Corporate gifts'
AND released = 1;

The goal was to retrieve unreleased products.

The Biggest Lesson

The application already has a SQL query.

I am NOT writing a brand new SQL query.

Instead, I inject my input into an existing query and change its meaning.

I can think of the query as a template:

SELECT *
FROM products
WHERE category = '[MY INPUT]'
AND released = 1;
Key Idea:
My job is to mentally reconstruct the final SQL statement after my input has been inserted.

Understanding the Payload

The successful payload was:

Corporate gifts' OR 1=1--

The application substituted the payload into the query:

SELECT *
FROM products
WHERE category = 'Corporate gifts' OR 1=1--'
AND released = 1;

Breaking It Down

Corporate gifts

Matches the expected category value.

'

Closes the original SQL string.

Before this quote, everything is treated as plain text.

After this quote, the database starts interpreting my input as SQL.

OR

Introduces another condition into the WHERE clause.

1=1

A Boolean expression that is always TRUE. 

category='Corporate gifts' OR TRUE

Since anything OR TRUE evaluates to TRUE, every row satisfies the condition.

--

Starts a SQL comment. Everything after it is ignored by the database.

The following part is never executed:

' AND released = 1;

This prevents the application's remaining SQL from affecting the query.

Why OR 1=1 Returns Every Row

Product Category Released
Teddy Gifts 1
Secret Toy Gifts 0
Phone Electronics 1
Prototype Electronics 0

The WHERE clause becomes:

category='Corporate gifts' OR 1=1

Every row evaluates like this:

FALSE OR TRUE
TRUE
Since 1=1 is always TRUE, every record in the table satisfies the WHERE clause, including unreleased products.

Mental Model I Will Use Going Forward

Instead of asking:

"What payload should I use?"

I will ask:

  1. What SQL query is the application generating?
  2. Which part of the query do I control?
  3. Am I inside a quoted string?
  4. How do I exit the string?
  5. What SQL do I want to inject?
  6. What SQL will the application append afterwards?
  7. Will the appended SQL break my injection?
  8. Do I need to neutralize the remaining SQL using a comment?
  9. What will the final SQL statement look like?
If I cannot reconstruct the final SQL query on paper, I should not send the payload yet.

Key Takeaways

  • SQL Injection is about modifying an existing SQL query—not creating a new one.
  • Always reconstruct the complete SQL statement before testing.
  • The single quote (') changes my role from providing data to writing SQL.
  • OR 1=1 is simply an expression that always evaluates to TRUE.
  • -- comments out the remainder of the application's SQL query.
  • Understanding how the SQL parser works is more valuable than memorizing payloads.
  • Every SQL Injection challenge becomes easier when I think like the database parser.

Personal Reflection

Today's lesson completely changed how I think about SQL Injection.

Previously, I believed successful SQL Injection depended on remembering payloads. Now I understand that every payload is simply the result of reasoning about how the application constructs its SQL query.

Going forward, my focus will be on reconstructing the server's final SQL statement before sending any request. Once I can visualize exactly what the database receives, crafting payloads becomes a logical process instead of a guessing game.
