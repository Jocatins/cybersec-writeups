Blind SQL Injection with Time Delays

Lab: Blind SQL injection with time delays PRACTITIONER LAB SOLVED

Lab Description

This lab contains a blind SQL injection vulnerability. The application uses a tracking cookie for analytics and performs a SQL query containing the value of the submitted cookie.

The results of the SQL query are not returned, and the application does not respond any differently based on whether the query returns any rows or causes an error. However, since the query is executed synchronously, it is possible to trigger conditional time delays to infer information.

Objective: Exploit the SQL injection vulnerability to cause a 10-second delay.

End Goal

To prove that the field is vulnerable to blind SQL injection (time-based) by triggering a measurable delay in the server's response.

Analysis

I began by reviewing the SQL Injection Cheat Sheet, specifically the time delays section, which provides database-specific payloads for introducing a deliberate pause in query execution.

Time Delay Payloads by Database

Database Payload
Oracle dbms_pipe.receive_message(('a'),10)
Microsoft WAITFOR DELAY '0:0:10'
PostgreSQL SELECT pg_sleep(10)
MySQL SELECT SLEEP(10)

Testing Procedure

The tracking cookie value was the injection point. The original cookie value was replaced with the following payloads to test each database's time-delay function. The response time was measured for each request.

PostgreSQL Test

' || (SELECT pg_sleep(10))--

Observed response time: 10563 ms (~10.5 seconds)

This confirms two things:

  • The backend database is PostgreSQL.
  • The parameter is vulnerable to blind SQL injection with time delays.

MySQL Test

' || (SELECT SLEEP(10))--

Observed response time: 433 ms

The query returned almost immediately, confirming that the backend is not MySQL (as expected, since the PostgreSQL payload already succeeded).

Result: The pg_sleep(10) payload caused a ~10-second delay, proving the parameter is vulnerable to time-based blind SQL injection and that the database engine is PostgreSQL.

Conclusion

The application is vulnerable to blind SQL injection via a time-delay technique. Because the query executes synchronously and no output or error differences are reflected back to the client, time-based inference is the only viable route to extract data. The successful payload ' || (SELECT pg_sleep(10))-- confirmed the vulnerability and identified the backend DBMS.
