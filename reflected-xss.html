Reflected XSS into Attribute with Angle Brackets HTML-Encoded

Platform: PortSwigger Web Security Academy

Difficulty: Apprentice

Vulnerability: Reflected Cross-Site Scripting (XSS)

Context: HTML attribute injection

1. Lab Objective

The application contains a reflected XSS vulnerability in the blog search functionality. The search parameter is reflected into an HTML attribute.

However, angle brackets are HTML-encoded, meaning a conventional payload such as <script>alert(1)</script> is not the appropriate approach.

The objective was to escape the existing HTML attribute and inject an event-handler attribute capable of executing JavaScript.

2. Initial Reconnaissance

I started by entering a unique alphanumeric string into the search functionality: 

nicholas123

The application reflected the input into the page. The important HTML was: 

<input type="text"
       placeholder="Search the blog..."
       name="search"
       value="nicholas123">

This immediately identified the injection context: 

value="nicholas123"
Key observation: The attacker-controlled search parameter is reflected inside a double-quoted HTML attribute.

3. Understanding the Context

The vulnerability was not DOM-based XSS like some of the previous labs I had worked on. There was no need to find a JavaScript source such as location.hash and no need to identify a JavaScript sink such as document.write().

Instead, the flow was: 

Search parameter
      ↓
Server-side reflection
      ↓
HTML response
      ↓
value="ATTACKER INPUT"
      ↓
HTML attribute injection
      ↓
JavaScript event handler
      ↓
XSS

4. Testing the Attribute Boundary

I tested how special characters were handled. A double quote was particularly important because the application placed the search parameter inside a double-quoted attribute.

Using: 

nicholas123"

resulted in HTML resembling: 

<input type="text"
       placeholder="Search the blog..."
       name="search"
       value="nicholas123" "">

This demonstrated that the double quote was not safely encoded and could terminate the existing value attribute.

5. Confirming Attribute Injection

Before attempting JavaScript execution, I used a harmless attribute injection to confirm that I could control the HTML structure. 

nicholas123" data-test="hello

The application produced: 

<input type="text"
       placeholder="Search the blog..."
       name="search"
       value="nicholas123"
       data-test="hello">

This was the critical confirmation. The original structure: 

value="nicholas123"

had effectively become: 

value="nicholas123" data-test="hello"

Therefore, I had successfully escaped the original attribute and injected a new attribute.

6. Choosing the XSS Technique

At this point, the important question became:

Can the injected attribute cause JavaScript execution?

HTML provides event-handler attributes that execute JavaScript when their corresponding browser event occurs.

For this lab, the relevant event was onmouseover.

The final proof-of-concept payload was: 

"onmouseover="alert(1)

7. Final Payload

When inserted into the search parameter, the resulting HTML became: 

<input type="text"
       placeholder="Search the blog..."
       name="search"
       value="nicholas123"
       onmouseover="alert(1)">

The payload therefore transformed the original HTML: 

<input value="nicholas123">

into: 

<input value="nicholas123" onmouseover="alert(1)">

The browser now treats onmouseover as an event handler. When the mouse is moved over the injected input element, the JavaScript executes.

8. Why the Attack Worked

The attack worked because the application trusted attacker-controlled data inside an HTML attribute.

The important sequence was: 

"nicholas123"
        ↓
Break out of value=""
        ↓
Inject onmouseover=""
        ↓
Browser interprets it as an event handler
        ↓
alert(1)
Core lesson: XSS payloads are highly dependent on context. The correct payload for JavaScript, HTML text, an HTML attribute, CSS, or a URL context can be completely different.

9. Why <script> Was Not Necessary

A common beginner assumption is that XSS means injecting: 

<script>alert(1)</script>

That is only one possible XSS technique.

Here, angle brackets were encoded, making tag injection ineffective. However, the attacker did not need to create a new HTML element. An existing <input> element could be modified by injecting an event-handler attribute.

This is why understanding the HTML parsing context is more valuable than memorizing a single XSS payload.

10. The Recon Process I Learned

My initial instinct was to search the page source for JavaScript or jQuery, similar to the DOM XSS labs I had previously studied. That was not the right approach for this vulnerability.

A better general workflow is:

Step Question
1. Find input Where can I control data?
2. Test reflection Does my input appear in the response?
3. Identify context Is it HTML text, an attribute, JavaScript, CSS, or a URL?
4. Test encoding Which characters are escaped?
5. Test boundaries Can I escape the current context?
6. Select technique Which browser feature can turn the injection into execution?
7. Test execution Does the payload execute under realistic conditions?

11. Real-World Application

This type of vulnerability can appear in real applications anywhere user-controlled data is inserted into HTML without context-appropriate output encoding.

Examples include:

  • Search pages that place the search term into an input's value.
  • Profile pages that insert usernames into HTML attributes.
  • Admin dashboards that populate data-* attributes.
  • Filtering interfaces that preserve query parameters in form fields.
  • Error pages that reflect an invalid parameter.
  • Applications that generate HTML templates using unsanitized user input.

12. Example Real-World Scenario

Imagine an application generates: 

<input value="USER_SEARCH">

If USER_SEARCH is inserted without appropriate HTML attribute encoding, an attacker may attempt to terminate the attribute and inject another attribute.

The impact depends on the application's security controls, browser behavior, authentication context, and where the vulnerable functionality is accessible.

A successful stored XSS vulnerability can be particularly serious because malicious input may persist and execute when other users view the affected page. Reflected XSS generally requires the victim to visit a crafted URL or otherwise submit attacker-controlled input.

13. Reflected vs Stored vs DOM XSS

Type Typical Flow
Reflected XSS Request parameter → Server → HTML response → Browser
Stored XSS Attacker input → Database → Victim's page → Browser
DOM XSS Client-side source → JavaScript sink → DOM → Browser

This lab was primarily a lesson in reflected XSS and HTML attribute context.

14. Important Lesson About Recon

One of the biggest lessons from this challenge was that reconnaissance should be proportional to the problem.

For a learning exercise, deeply investigating every character can be useful. However, in practical security testing, repeatedly performing exhaustive recon when the injection context is already obvious can become inefficient.

Once the following pattern is recognized: 

User input
    ↓
Reflected
    ↓
Quoted HTML attribute
    ↓
Quote is not encoded

an experienced tester should immediately consider: 

Attribute breakout
        ↓
Injected attribute
        ↓
Event-handler attributes
        ↓
Execution

The skill is therefore not memorizing one payload. The skill is recognizing the context → breakout → execution pattern.

15. Key Takeaways

  • XSS is context-dependent.
  • Finding JavaScript source code is not necessary for reflected XSS.
  • Always determine where attacker-controlled input is reflected.
  • Identify the exact HTML/JavaScript/CSS/URL context.
  • Test how special characters are encoded.
  • A double quote can be significant when input is inside a double-quoted attribute.
  • Angle brackets being encoded does not automatically eliminate XSS.
  • Existing HTML elements can sometimes be turned into execution points through event-handler attributes.
  • A payload that executes during your manual testing may not execute automatically for another user.
  • For real-world testing, always consider how the victim actually interacts with the application.
My mental model going forward:

Don't start by asking: "What XSS payload should I use?"

Start by asking: "Where does my input land, what context am I in, and what boundary can I escape?"

Once the context is known, the appropriate class of payload becomes much easier to identify.
