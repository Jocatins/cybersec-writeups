Stored XSS into Anchor href Attribute with Double Quotes HTML-Encoded

A practical, beginner-friendly writeup for understanding the vulnerability, reproducing it with Burp Suite, and developing a reusable XSS investigation methodology.

1. Lab objective

The application contains a comment feature with a Website input. The submitted Website value is stored and later inserted into the author’s anchor element.

The goal is to submit a comment that causes alert(1) to execute when the comment author’s name is clicked.

Core lesson: Identify where your input lands, understand how the browser interprets that context, and choose a context-appropriate proof of concept.

2. Understand the data flow

1. User input
Website field receives a value such as nic123abc.
↓
2. HTTP request
The browser submits the value in a form parameter.
↓
3. Server storage
The application saves the comment and Website value.
↓
4. HTML rendering
The saved value is placed inside an anchor’s href.
↓
5. Browser execution
Clicking the link activates the JavaScript URL.

3. Reconnaissance: Start with a harmless marker

Do not begin by randomly trying complex payloads. First establish where the input is reflected.

FieldExample

Use a unique alphanumeric marker because it is easy to search for in Burp responses and page source.

If the page later contains:

<a id="author" href="nic123abc">nic</a>

you have confirmed that your Website value is reflected inside an anchor URL attribute.

4. Configure Burp Suite

  1. Open Burp Suite.
  2. Go to Proxy → Intercept.
  3. Turn interception on.
  4. Open the PortSwigger lab in the browser.
  5. Submit a normal comment containing your unique Website marker.
  6. Inspect the intercepted request and locate the parameter containing your marker.
  7. Right-click the request and choose Send to Repeater.

An illustrative request may look like this:

POST /post/comment HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

csrf=TOKEN&postId=1&comment=Testing+123&name=nic&email=test%40example.com&website=nic123abc

Note: Your actual endpoint, parameters, CSRF token, and host will differ. Use the request captured from your own lab.

5. Inspect the stored response

The comment submission response may not contain the saved comment. Make a second request to view the blog post, intercept it, and send it to another Repeater tab.

Search the response for your unique marker:

nic123abc

You may find:

<section class="comment">
    <p>
        <img src="/resources/images/avatarDefault.svg" class="avatar">
        <a id="author" href="nic123abc">nic</a>
        | 15 September 2026
    </p>
    <p>Testing 123</p>
    <p></p>
</section>

The important discovery is that the value appears in:

<a href="USER_INPUT">nic</a>

That is an anchor URL attribute context, not ordinary HTML text and not necessarily JavaScript source code.

6. Why the lab title mentions double quotes being HTML-encoded

The application may encode a submitted quote as &quot;. This prevents the quote from acting as a new HTML attribute delimiter.

For example, an attempted injection might be rendered as:

<a href="&quot; onmouseover=&quot;alert(1)">nic</a>

The encoded quote is treated as data inside the attribute value rather than as the end of the attribute.

Important insight: You do not always need to break out of an HTML attribute. If your input is already being interpreted as a URL, the URL scheme itself may be the relevant attack surface.

7. Understand the payload

javascript:alert(1)
PartMeaning
javascript:A URL scheme that can execute JavaScript when the link is activated, where permitted by the browser and security policy.
alert(1)A visible JavaScript proof of execution.

When the application renders:

<a id="author" href="javascript:alert(1)">nic</a>

the browser treats the anchor destination as a JavaScript URL. Clicking the author name can therefore execute the payload.

A payload such as <script>alert(1)</script> is not the natural first choice here because the input is inside an href attribute, not inserted as HTML content.

8. Reproduce the lab in Burp Repeater

  1. Return to the comment submission request in Repeater.
  2. Replace the Website value nic123abc with javascript:alert(1).
  3. When represented as URL-encoded form data, it may appear as:
website=javascript%3Aalert%281%29

The decoded value is:

javascript:alert(1)

Send the request. Then return to the blog post and refresh or revisit the page to load the stored comment.

9. Confirm the stored HTML

Inspect the author link. The expected result is similar to:

<a id="author" href="javascript:alert(1)">nic</a>

Your observed output was:

<section class="comment">
    <p>
        <img src="/resources/images/avatarDefault.svg" class="avatar">
        <a id="author" href="javascript:alert(1)">nic</a> | 15 September 2026
    </p>
    <p>javascript:alert(1)</p>
    <p></p>
</section>

The comment body displaying the payload is not the execution proof. The important reflection is the author anchor’s href.

10. Verify execution

  1. Right-click the author name.
  2. Select Copy Link Address or Copy URL, depending on the browser.
  3. Paste the copied destination somewhere safe to inspect it.
  4. Confirm that the destination is javascript:alert(1).
  5. Click the author name.
  6. Observe the alert dialog containing 1.
Successful verification: The author link activates the JavaScript URL and displays the alert dialog. This satisfies the lab objective.

11. A reusable XSS investigation method

  1. Map the application: Identify pages, forms, parameters, and user-controlled fields.
  2. Insert a unique marker: Use a random value such as nic123abc.
  3. Intercept with Burp: Find the HTTP parameter carrying the marker.
  4. Follow the data: Search responses and the DOM for the marker.
  5. Classify the context: HTML text, HTML attribute, JavaScript string, URL, or DOM sink.
  6. Study transformations: Check encoding, filtering, sanitization, and decoding.
  7. Choose a context-specific proof: Use a harmless payload appropriate to the authorized lab.
  8. Verify the exact sink: Confirm which element or operation causes execution.
  9. Record the finding: Write down source, parameter, reflection, context, sink, payload, and impact.

13. Reflected XSS vs stored XSS

Payload is sent in a request and reflected in the immediate response.Payload is saved and later served to users viewing the affected content.
Often requires a victim to visit a crafted URL or submit a request.May affect multiple users who view the stored content.

14. Inspecting the anchor and scripts

Inspect the anchor in DevTools

  1. Right-click the author name.
  2. Select Inspect.
  3. Find the <a> element.
  4. Examine its href attribute.

Inspect the raw response in Burp

Compare the server response with the final DOM. This helps distinguish server-side rendering from client-side JavaScript manipulation.

Inspect JavaScript files

In DevTools → Sources, look for code that reads the Website field, builds comment markup, assigns href, uses innerHTML, or handles click events.

Do not assume: The presence of a script file does not automatically mean it caused the vulnerability. In this lab, the decisive evidence is the stored value becoming the anchor destination.

15. Common beginner mistakes

  • Starting with a script tag: It may not execute when placed inside an attribute.
  • Trying to escape with quotes immediately: Quotes may be HTML-encoded.
  • Focusing only on the comment body: Text inside a paragraph is not automatically executable.
  • Inspecting only the submission response: The stored comment may appear only when viewing the post.
  • Assuming every href is safe: URL schemes matter.
  • Using a payload without understanding it: Every payload should have a reason tied to the sink and context.

16. Defensive lessons for developers

An application should not blindly trust a Website field.

Unsafe pattern

const html = `
  <a href="${website}">${name}</a>
`;

Validate allowed URL schemes

function isSafeWebsite(value: string): boolean {
  try {
    const url = new URL(value);

    return url.protocol === "http:" ||
           url.protocol === "https:";
  } catch {
    return false;
  }
}

This is an example of URL scheme validation, not a complete production security policy.

Prefer safe DOM APIs

const link = document.createElement("a");

link.textContent = name;
link.href = safeWebsite;

container.appendChild(link);

Additional defenses include server-side validation, context-appropriate output encoding, avoiding untrusted HTML in innerHTML, applying a suitable Content Security Policy, and safely rendering stored comments.
