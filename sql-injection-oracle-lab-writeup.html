SQL Injection Attack: Listing Database Contents on Oracle

Lab status: Solved without checking the solution. The main goal was not just to obtain the administrator credentials, but to understand how each payload was constructed and why it worked.

1. Objective

The PortSwigger Web Security Academy lab contained a SQL injection vulnerability in the product category filter. The application returned the results of the SQL query in its response, allowing a UNION-based SQL injection attack. The database was Oracle, and the objective was to discover the credentials table, identify its columns, retrieve the credentials, and log in as the administrator.

2. Confirming SQL Injection

The first step was to test whether the category parameter was injectable. A single quote was appended to the category value: 

Corporate gifts'

The application returned an HTTP 500 Internal Server Error. This indicated that the quote was affecting the underlying SQL syntax and provided evidence that the parameter was injectable.

3. Determining the Number of Columns

Before using UNION SELECT, we needed to determine how many columns the original query returned. We tested ORDER BY incrementally: 

' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--

ORDER BY 1 and ORDER BY 2 worked, while ORDER BY 3 produced an error. Therefore, the original query returned two columns.

4. Confirming a Two-Column UNION

Because the original query returned two columns, our UNION query also needed to return two columns. The lab was running Oracle, where SELECT statements require a FROM clause. Oracle's built-in DUAL table can be used when a real table is not required. 

' UNION SELECT 'abc','def' FROM dual--

The response displayed both values:

abc    def

This confirmed that the UNION injection worked and that both columns were reflected in the application's response.

5. Confirming the Oracle Database

We queried Oracle's version information using the v$version view and its BANNER column: 

' UNION SELECT banner, NULL FROM v$version--

The response revealed Oracle Database 11g Express Edition, version 11.2.0.2.0, along with other Oracle component versions.

6. Enumerating Database Tables

Instead of guessing the name of the credentials table, we used Oracle's metadata. ALL_TABLES is an Oracle data-dictionary view containing information about accessible tables, while TABLE_NAME identifies those tables. 

' UNION SELECT table_name, NULL FROM all_tables--

Among the returned table names was:

USERS_ANOYDF

This was the table that appeared to contain the application's user credentials.

7. Enumerating the Table's Columns

Next, we queried Oracle's column metadata. ALL_TAB_COLUMNS contains information about columns, including their names in COLUMN_NAME. We filtered the metadata to the table we had discovered: 

' UNION SELECT COLUMN_NAME, NULL
FROM ALL_TAB_COLUMNS
WHERE TABLE_NAME = 'USERS_ANOYDF'--

The response revealed two relevant columns:

Column
USERNAME_KJTNFZ
PASSWORD_QXTYIC

8. Extracting the Credentials

We now had the table name and both column names. The final UNION query selected the username and password values: 

' UNION SELECT USERNAME_KJTNFZ, PASSWORD_QXTYIC FROM USERS_ANOYDF--

The application returned the contents of the credentials table. We then used the administrator credentials to complete the lab.

9. What I Actually Learned

  • SQL injection is easier to understand when the underlying SQL structure is reasoned about rather than when payloads are memorized.
  • ORDER BY can be used to determine the number of columns returned by a query.
  • A UNION query must return the same number of columns as the original query.
  • Oracle requires a FROM clause for SELECT statements, making DUAL useful for test queries.
  • Oracle's data dictionary can be used to enumerate database structure.
  • ALL_TABLES helped identify the target table, while ALL_TAB_COLUMNS helped identify its columns.
  • Understanding the difference between SQL identifiers and string literals is essential. For example, COLUMN_NAME is an identifier, while 'USERS_ANOYDF' is a string value.
  • The most valuable lesson was recognizing patterns and constructing the next payload from information discovered in the previous step.

Key takeaway: The objective was not to memorize a final payload. Each payload was built from the result of the previous investigation. That pattern-recognition approach makes SQL injection techniques much easier to understand and reproduce in authorized labs.
