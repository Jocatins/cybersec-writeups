SQL Injection UNION Attack — Determining the Number of Columns

Lab: SQL injection UNION attack, determining the number of columns returned by the query

Difficulty: Practitioner

Objective: Determine the number of columns returned by the application's SQL query by using a UNION SELECT injection containing NULL values.

Objective

The purpose of this lab was to determine how many columns were being returned by the vulnerable SQL query behind the product category filter.

A UNION attack requires both queries to return the same number of columns. Therefore, before attempting to retrieve information from another table, we first needed to determine the number of columns in the original query.

Step 1 — Identifying the Injection Point

The lab indicated that the vulnerability existed in the product category filter.

We intercepted the request using Burp Suite and sent it to Repeater so that we could modify the category parameter and observe the application's responses.

The parameter was conceptually similar to:

category=Gifts

Because the application was vulnerable to SQL injection, we could manipulate the value supplied to this parameter.

Step 2 — Understanding the UNION Technique

The important concept behind this attack is that a SQL UNION combines the results of two SELECT statements.

For example:

SELECT column1, column2, column3
FROM products
WHERE category = 'Gifts'

could potentially be combined with:

UNION SELECT NULL, NULL, NULL

However, the number of columns must match.

For example, if the original query returns three columns: 

SELECT column1, column2, column3

then this would be valid:

UNION SELECT NULL, NULL, NULL

while this would not:

UNION SELECT NULL, NULL

because the second query only contains two columns.

Step 3 — Testing Different Numbers of Columns

We started by injecting a UNION SELECT containing a single NULL value: 

' UNION SELECT NULL--

The application returned an HTTP 500 error.

This suggested that the number of columns in our injected query did not match the number of columns returned by the original query.

We then increased the number of NULL values:

' UNION SELECT NULL,NULL--

This also resulted in an HTTP 500 error.

Next, we tried:

' UNION SELECT NULL,NULL,NULL--

This time, the application returned the successful response:

Congratulations, you have solved the lab.

Finally, the four-column attempt was also tested: 

' UNION SELECT NULL,NULL,NULL,NULL--

It returned an HTTP 500 error.

Step 4 — Interpreting the Results

Our observations were:

Payload Result
' UNION SELECT NULL-- HTTP 500
' UNION SELECT NULL,NULL-- HTTP 500
' UNION SELECT NULL,NULL,NULL-- Lab solved
' UNION SELECT NULL,NULL,NULL,NULL-- HTTP 500

The important result was: 

' UNION SELECT NULL,NULL,NULL--

The successful response tells us that the injected SELECT contained the correct number of columns.

Conclusion: The original SQL query returns 3 columns.

Why NULL Was Used

We used NULL because we were not yet interested in retrieving actual data.

At this stage, our only goal was to determine the number of columns.

Using NULL also avoids having to immediately know the data type expected by each column.

Later in a UNION-based SQL injection, we may replace these NULL values with actual expressions or database information.

For example:

UNION SELECT username, password, NULL

But that would only make sense after determining the number of columns and understanding which columns can accept the data we want to retrieve.

Understanding the Successful Payload

Our successful payload was:

' UNION SELECT NULL,NULL,NULL--

Conceptually, the original query could have looked something like: 

SELECT column1, column2, column3
FROM products
WHERE category = 'Gifts'

Our injection modifies the query so that the database attempts to execute something equivalent to: 

SELECT column1, column2, column3
FROM products
WHERE category = 'Gifts'
UNION
SELECT NULL,NULL,NULL
--'

The -- begins a SQL comment, causing the remainder of the original query to be ignored.

Most importantly, both SELECT statements contain three columns, allowing the UNION operation to succeed.

Key Lesson

This lab demonstrated one of the fundamental steps in a UNION-based SQL injection attack:

Before retrieving data with UNION SELECT, determine how many columns the original query returns.

We discovered the number of columns by gradually increasing the number of NULL values until the database accepted the UNION query.

The successful payload was:

' UNION SELECT NULL,NULL,NULL--

Therefore, the vulnerable query returns: 

3 columns

What I Learned

  • How UNION SELECT can be used to interact with the results of an existing SQL query.
  • Why the number of columns in both queries must match.
  • How HTTP 500 responses can provide useful feedback during SQL injection testing.
  • Why NULL values are useful when determining the number of columns.
  • How SQL comments such as -- can be used to terminate the remainder of the original query.
  • Most importantly, I learned why the payload works instead of simply memorizing it.
