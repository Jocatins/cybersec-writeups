Beyond Payloads: Learning to Think Like a Penetration Tester

Today's lab was completed on PortSwigger Web Security Academy. Unlike previous Capture-The-Flag (CTF) exercises where the objective was simply to retrieve a flag, this exercise focused on understanding the methodology behind identifying, validating, and exploiting a SQL Injection vulnerability protected by a Web Application Firewall (WAF).

Lab

SQL Injection with Filter Bypass via XML Encoding

Objective

  • Identify an SQL Injection vulnerability hidden inside an XML request.
  • Understand why a WAF blocks obvious SQL Injection payloads.
  • Learn XML encoding techniques to bypass request filtering.
  • Extract administrator credentials from the database.

Initial Observation

While browsing the vulnerable e-commerce application, clicking "Check Stock" generated the following request: 

POST /product/stock

<stockCheck>
    <productId>3</productId>
    <storeId>2</storeId>
</stockCheck>

This immediately revealed that user input was submitted in XML format, making XML parsing a potential attack surface.

First Hypothesis

I initially assumed the vulnerability existed inside the storeId parameter. The first payload attempted was: 

2'

Result: 

HTTP 403
Attack detected

This strongly suggested that a Web Application Firewall (WAF) was inspecting requests before they reached the application.

Understanding the WAF

Rather than immediately searching for exploit payloads, I spent time understanding why the request failed. I researched:

  • XML special characters
  • Named XML entities
  • Numeric character references
  • How XML parsers decode input
  • How WAFs inspect requests

This research introduced two important concepts.

Type Example
Named Entity &apos;
Numeric Entity &#39;
Hexadecimal Entity &#x27;

Installing Hackvertor

The PortSwigger lab recommended the Hackvertor Burp extension. Unfortunately, installation repeatedly crashed Burp Suite. After several attempts and troubleshooting, the extension was successfully installed.

This introduced another useful lesson:

Professional penetration testing is often less about exploiting vulnerabilities and more about troubleshooting tooling.

Encoding SQL Payloads

Using Hackvertor, I learned how payloads could be transformed into numeric XML entities.

Example: 

Original

' ORDER BY 1--

Encoded

' ORDER BY 1--

After XML parsing, the backend reconstructs the original SQL payload.

Testing the WAF

The encoded payload successfully bypassed the WAF. Instead of receiving: 

403 Attack detected

the application returned: 

HTTP 200

0 units

This demonstrated that the filter had been bypassed, even though the SQL Injection itself had not yet been confirmed.

Mistakes Along the Way

  • Attempted SQL Injection before confirming whether input was evaluated.
  • Assumed the application used quoted SQL values.
  • Encoded the entire payload instead of understanding keyword obfuscation.
  • Focused on payloads before understanding application behaviour.

Official Solution Analysis

After extensive testing, I compared my methodology with the official PortSwigger solution. The biggest insight was that the solution first proved the application evaluated expressions.

Example: 
1+1

Instead of immediately injecting SQL. Only after proving evaluation did the solution move to UNION SELECT attacks. This reinforced the importance of methodology over memorised payloads.

Major Lessons Learned

  • Always understand the application before attempting exploitation.
  • Never assume the SQL query structure.
  • Validate whether input is interpreted or treated as plain text.
  • Researching protocols often reveals bypass opportunities.
  • XML parsing occurs before backend SQL execution.
  • Numeric XML entities can bypass keyword-based filtering.
  • Hackvertor automates payload encoding but should not replace understanding.
  • A WAF bypass is not the same as a successful SQL Injection.
  • Methodology is more valuable than memorised payloads.

Biggest Personal Takeaway

Today's exercise changed my mindset. Instead of asking: "What payload should I use?" I found myself asking: "How can I prove my assumptions before attempting exploitation?" That shift represents the difference between simply solving CTF challenges and thinking like a professional penetration tester.

Although I eventually reviewed the official solution, the majority of the learning came from the investigation itself. The process involved observing application behaviour, forming hypotheses, testing them, researching unfamiliar technologies, and adapting my approach based on evidence. The greatest lesson was not learning a SQL Injection payload, but learning to approach web application security as a structured investigative process.
