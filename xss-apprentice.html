Cross-Site Scripting (XSS) — Apprentice Lab Notes

These notes document the XSS challenges completed so far and focus on understanding why the payload works, how payloads are constructed, how the browser interprets them, attacker impact, and defensive techniques.

Core XSS principle: XSS occurs when attacker-controlled data reaches a browser execution context without being handled safely, allowing the attacker to influence what the browser interprets as HTML or JavaScript.

1. The Three Questions to Ask in Every XSS Lab

Instead of memorising payloads, start every XSS investigation with:

  1. Where is my input coming from? — the source.
  2. Where does my input end up? — the sink.
  3. How is the browser interpreting it? — the context.

The context is particularly important because an XSS payload designed for an HTML context may fail completely when the input is placed inside a JavaScript string or an HTML attribute. 

SOURCE
  ↓
Attacker-controlled input
  ↓
Application processing
  ↓
SINK
  ↓
Browser parser
  ↓
Execution

2. Reflected XSS into HTML Context with Nothing Encoded

Vulnerability

The search functionality reflects user-controlled input directly into the HTML response without encoding it.

Because the input is placed directly into an HTML context, HTML supplied by the attacker is interpreted as markup instead of ordinary text.

Payload Used

<script>alert(1)</script>

Why Does It Work?

The payload consists of three important components: 

<script>
↓
Start a JavaScript element

alert(1)
↓
JavaScript to execute

</script>
↓
Close the JavaScript element

The vulnerable application effectively produces something conceptually similar to: 

<div>
Search results for:
<script>alert(1)</script>
</div>

The browser parses the injected string as HTML. The <script> element therefore becomes executable JavaScript.

How Was the Payload Constructed?

The important observation was that the injection point was already an HTML context. 

HTML context
↓
Can I introduce an HTML element?
↓
<script>
↓
Can I execute JavaScript?
↓
alert(1)
↓
Close the element
↓
</script>
Lesson: When attacker input is inserted directly into an HTML context with no encoding, a simple HTML element containing JavaScript may be sufficient.

3. Stored XSS into HTML Context with Nothing Encoded

Vulnerability

The application accepts comments and stores them. When another user views the blog post, the stored comment is rendered into the page without appropriate output encoding.

Payload Used

<script>alert(1)</script>

Why Is This Different From Reflected XSS?

Reflected XSS Stored XSS
Input is reflected as part of the immediate response. Input is stored by the application and rendered later.
Often requires the victim to visit a crafted URL. The malicious content can persist on the application.
Payload usually travels through the request. Payload travels through application storage.

Attack Flow

Attacker
↓
Submit malicious comment
↓
Application stores comment
↓
Victim opens blog post
↓
Application retrieves comment
↓
Comment inserted into HTML
↓
Browser interprets injected markup
↓
JavaScript executes

Why the Payload Works

The payload is identical to the reflected XSS example because the HTML context is the same.

The difference is the lifetime and delivery mechanism of the malicious input, not necessarily the syntax of the payload.

Important: Stored XSS can be particularly dangerous because the attacker does not necessarily need to repeatedly convince victims to visit a specially crafted URL. The malicious content can remain in the application until it is removed.

4. DOM XSS — document.write() Sink Using location.search

Vulnerability

This vulnerability exists entirely in client-side JavaScript. The application takes attacker-controlled data from location.search and passes it to document.write().

Source

location.search

The query string is attacker-controlled because the attacker can place arbitrary data in the URL.

Sink

document.write()

document.write() can cause supplied data to be interpreted as HTML.

First Step — Use a Canary

Rather than immediately attempting XSS, first enter a harmless, recognisable string such as: 

test123

Inspect the DOM and determine where the value appears. In this lab it appears inside an image attribute similar to: 

<img src="...searchTerms=test123">

Identify the Context

The input is inside a double-quoted HTML attribute: 

<img src="USER_INPUT">

Therefore, inserting another HTML element immediately is not enough. The first objective is to escape the attribute context.

Payload Used

"><svg onload=alert(1)>

How Was It Constructed?

The payload can be understood as a sequence:

"
↓
Escape the quoted src attribute

>
↓
Finish the HTML element

<svg ...>
↓
Create a new HTML element

onload=alert(1)
↓
Execute JavaScript when the SVG loads

Conceptually, the attacker is transforming: 

<img src="ATTACKER_INPUT">

into something equivalent to:

<img src="">
<svg onload=alert(1)>
Key lesson: The payload was not chosen randomly. It was constructed from the injection context: first escape the attribute, then introduce an executable HTML element.

5. DOM XSS — innerHTML Sink Using location.search

Vulnerability

The application retrieves attacker-controlled data from location.search and assigns it to an element using innerHTML.

Source

location.search

Sink

element.innerHTML

Payload Used

<img src=1 onerror=alert(1)>

Why Does It Work?

Unlike the previous document.write() lab, we do not necessarily need to escape an existing quoted attribute first. The input is being interpreted as HTML by innerHTML.

The payload creates an image:

<img src=1>

The source value is deliberately invalid in the lab context, causing an image loading error.

That error triggers:

onerror=alert(1)

The browser therefore executes alert(1) when the error event fires.

Payload Construction

<img
↓
Create an HTML element

src=1
↓
Give it a source that will fail in the lab

onerror=
↓
Use an event handler triggered by the failure

alert(1)
↓
JavaScript execution
Important: This demonstrates why understanding browser events is useful when studying XSS. JavaScript execution does not always require a <script> element.

7. The Payload Construction Method

A major lesson from these labs is that payload construction should be context-driven.

Step 1 — Find the Source

Look for attacker-controlled data such as:

location.search
location.hash
location.href
document.URL
form input
query parameters
stored comments
profile fields

Step 2 — Find the Sink

Look for dangerous operations such as:

innerHTML
outerHTML
document.write()
insertAdjacentHTML()
eval()
setTimeout()

Step 3 — Determine the Context

Ask where your input appears:

HTML text?
HTML attribute?
JavaScript string?
JavaScript code?
URL?
CSS?

Step 4 — Determine What Must Be Escaped

If your input appears inside a quoted attribute, you may first need to escape the quotation mark.

If your input is already interpreted as HTML, you may be able to introduce an element directly.

Step 5 — Choose an Execution Mechanism

The execution mechanism depends on what the browser will accept in that context. Examples studied in these labs include: 

<script>...</script>

event handlers such as:
onerror=
onload=

Step 6 — Prove Execution Safely

In PortSwigger labs, alert(1) is deliberately used as a harmless proof of JavaScript execution.

Professional mindset: Do not begin by asking "What payload bypasses this?" Begin by asking "What parser is interpreting my input?"

8. Why XSS Is Dangerous in Real Applications

In these labs, the goal is simply to trigger alert(1). In a real application, an attacker could potentially execute JavaScript with the privileges of the vulnerable origin.

Potential Impact

  • Modify page content presented to the victim.
  • Perform actions using the victim's authenticated browser session.
  • Read sensitive information available to JavaScript on the page.
  • Modify forms or redirect users to attacker-controlled destinations.
  • Display convincing phishing interfaces inside a trusted origin.
  • Interact with application APIs using the victim's browser context.
Important distinction: XSS does not automatically mean "the attacker can steal every cookie." Modern defenses such as HttpOnly cookies, SameSite settings, CSP, and browser isolation can limit particular attack paths. The fundamental problem is that attacker-controlled JavaScript is executing in a trusted origin.

9. Real-World XSS Attack Scenarios

Scenario A — Reflected XSS

Imagine an application that reflects a search parameter directly into its response: 

https://example.com/search?q=USER_INPUT

If the application inserts that value into HTML without appropriate encoding, an attacker could attempt to construct a URL that causes JavaScript execution when a victim visits it.

This is why reflected XSS frequently appears in phishing-style attack chains: the malicious content can be delivered through a crafted link.

Scenario B — Stored XSS

Consider a forum, support system, social platform, CMS, or admin dashboard where users can submit content. 

Attacker
   ↓
Malicious content
   ↓
Application database
   ↓
Victim views content
   ↓
Browser renders malicious content

Stored XSS can have a larger blast radius because multiple users may encounter the malicious content.

Scenario C — DOM XSS

A modern single-page application might retrieve information from the URL and dynamically place it into the DOM. 

URL
 ↓
location.search
 ↓
JavaScript
 ↓
innerHTML
 ↓
DOM

The server may never see the malicious value. This is why DOM XSS can be missed if testing focuses exclusively on server responses.

10. How Developers Defend Against XSS

1. Prefer Safe DOM APIs

Instead of:

element.innerHTML = userInput;

prefer:

element.textContent = userInput;

textContent treats the value as text rather than parsing it as HTML.

2. Context-Aware Output Encoding

Output should be encoded according to where it is inserted. HTML, HTML attributes, JavaScript, CSS, and URLs have different parsing rules.

A common mistake is assuming that one generic "escape" function is safe everywhere.

3. Avoid Dangerous DOM Sinks

Be especially careful with:

innerHTML
outerHTML
document.write()
insertAdjacentHTML()
eval()

4. Sanitize HTML When HTML Is Actually Required

If an application genuinely needs to allow users to submit HTML, sanitization should remove dangerous constructs while preserving the allowed formatting.

5. Use Content Security Policy

A strong CSP can significantly reduce the impact of XSS by restricting where scripts can come from and, when configured appropriately, blocking inline script execution.

6. Protect Cookies

Authentication cookies should generally use security attributes such as HttpOnly, Secure, and appropriate SameSite settings.

HttpOnly is particularly useful because it prevents JavaScript from directly reading the cookie value.

7. Framework Protections

Modern frameworks such as React generally escape interpolated values by default. Developers can accidentally bypass these protections when using mechanisms such as raw HTML rendering. 

Dangerous pattern:

dangerouslySetInnerHTML

Always question why raw HTML is necessary.

11. Testing XSS in Real-Life Security Work

Only test applications you own or have explicit authorization to assess.

A professional XSS assessment can follow this methodology:

  1. Map input points.
  2. Identify reflected and stored data.
  3. Inspect the DOM and JavaScript.
  4. Identify sources and sinks.
  5. Determine the injection context.
  6. Use harmless canary values.
  7. Construct a minimal proof-of-concept.
  8. Demonstrate impact without accessing unnecessary data.
  9. Document the vulnerable code path.
  10. Recommend a context-appropriate fix.

Concept What the labs taught me
Reflected XSS User input can become executable HTML when reflected into a response without appropriate encoding.
Stored XSS Malicious input can persist in application storage and execute when another user views the affected content.
DOM XSS Client-side JavaScript can introduce XSS even when the server itself does not directly reflect the malicious input.
document.write() Understanding the exact HTML context is essential because the payload may need to escape an existing attribute before introducing new markup.
innerHTML HTML parsing can turn attacker-controlled strings into actual DOM elements, including elements with event handlers.

14. Final Takeaway

The most important thing I have learned from these XSS labs is not the payload itself — it is how to reason about the browser's parser.

The same alert(1) objective can require completely different payload structures depending on whether the attacker-controlled value appears in HTML text, an HTML attribute, JavaScript, a URL, or another execution context.

My methodology should therefore be: 

SOURCE
↓
SINK
↓
CONTEXT
↓
ESCAPE / BREAK CONTEXT
↓
CONTROLLED HTML / JS
↓
PROOF OF EXECUTION
↓
IMPACT
↓
REMEDIATION

This approach is more valuable than memorising a list of XSS payloads because it can be applied to unfamiliar applications and different vulnerability contexts.
