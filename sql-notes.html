SQL Injection (SQLi) – Learning Notes

SQL Injection is a web security vulnerability that occurs when an application incorporates untrusted user input into SQL queries without safely separating data from SQL instructions.

1. What is SQL Injection?

SQL Injection allows an attacker to interfere with the SQL queries made by an application. Depending on the vulnerability, this can allow unauthorized access to data, modification or deletion of database records, and in some cases further compromise of the underlying infrastructure.

Sensitive information that may be exposed includes:

  • Passwords
  • Credit card details
  • Personal user information
Key idea: The problem is not simply that an attacker enters unexpected characters. The real problem is that the application's input becomes part of the SQL query structure.

2. How SQL Injection Happens

Consider an application that displays products based on a category.

The application might receive:

https://insecure-website.com/products?category=Gifts

The server could construct:

SELECT * FROM products
WHERE category = 'Gifts'
AND released = 1;

Here, released = 1 prevents unreleased products from being displayed.

If the application directly concatenates the user's input into the query, the input may be able to alter the query's logic.

3. Detecting SQL Injection

SQL Injection can be investigated systematically by testing application inputs and observing how the response changes.

  • Submit a single quote (') and look for errors or unusual behavior.
  • Test SQL expressions that should produce the original value and compare the responses.
  • Test Boolean conditions such as OR 1=1 and OR 1=2 and compare the results.
  • For blind SQL injection, investigate differences in response time.
  • In appropriate testing environments, OAST techniques can be used to detect out-of-band interactions.

4. Where Can SQL Injection Occur?

SQL Injection commonly occurs inside a WHERE clause, but it isn't limited to SELECT queries.

  • SELECT: table names, column names, WHERE clauses, ORDER BY
  • INSERT: inserted values
  • UPDATE: updated values or WHERE clauses
Lesson: Always identify where the user's input enters the SQL statement before deciding what type of SQL injection technique applies.

5. Retrieving Hidden Data

One common SQL Injection scenario involves modifying a query so that it returns records that the application normally hides.

Original query:

SELECT * FROM products
WHERE category = 'Gifts'
AND released = 1;

A classic SQL comment technique can cause the remainder of the query to be ignored: 

Gifts'--

This can result in a query conceptually similar to:

SELECT * FROM products
WHERE category = 'Gifts'--'
AND released = 1;

The SQL comment causes the remaining portion of the statement to be treated as a comment. Therefore, the released = 1 restriction is no longer applied.

6. Boolean-Based Logic

Another technique is to introduce a condition that evaluates to true. 

Gifts' OR 1=1--

The resulting query can become:

SELECT * FROM products
WHERE category = 'Gifts'
OR 1=1--'
AND released = 1;

Since 1=1 is always true, the query can return all records accessible through that query.

Important: Never assume that OR 1=1 is harmless. If the same user-controlled input is used in another query, such as an UPDATE or DELETE statement, changing the logic could cause unintended modification or deletion of data.

7. SQL Injection Authentication Bypass

SQL Injection can also be used to interfere with authentication logic.

Imagine a login system that receives: 

Username: wiener
Password: bluecheese

The application might execute:

SELECT * FROM users
WHERE username = 'wiener'
AND password = 'bluecheese';

The application considers the login successful when the query returns a matching user.

In the deliberately vulnerable lab, the username input can be manipulated so that the password portion of the query becomes a SQL comment. 

administrator'--

The query becomes conceptually:

SELECT * FROM users
WHERE username = 'administrator'--'
AND password = '';

The password condition is therefore excluded from the SQL statement, allowing the query to match the administrator account.

Core lesson: The important thing to understand is not the payload itself. Understand how the application's original SQL query is constructed and how the injected input changes its logic.

8. UNION-Based SQL Injection

When an application returns the results of a SQL query, a UNION attack can sometimes be used to append the results of another SELECT statement.

For example:

SELECT name, description
FROM products
WHERE category = 'Gifts';

A UNION-based injection can conceptually add another query: 

' UNION SELECT username, password FROM users--

If the query structure and column requirements are compatible, the response may include data from the additional table.

Important concept: UNION attacks depend on the structure of the original query, including the number and compatible types of columns.

9. Blind SQL Injection

Blind SQL Injection occurs when the application does not directly return the SQL query results or database error details.

Even without seeing the database output, an attacker may infer information by observing changes in application behavior.

Common approaches

  • Boolean conditions that produce different responses.
  • Conditions that cause detectable database errors.
  • Time-based conditions that introduce measurable delays.
  • Out-of-band interactions detected through OAST techniques.

10. First-Order vs Second-Order SQL Injection

First-Order SQL Injection

The application receives user input through an HTTP request and immediately incorporates that input unsafely into a SQL query.

Second-Order SQL Injection

The application initially stores the user's input safely. Later, another part of the application retrieves that stored value and uses it unsafely inside a SQL query.

Key difference: First-order injection happens during the initial request. Second-order injection involves stored data being used unsafely later.

11. Database Differences

SQL Injection techniques can vary depending on the database platform. Important differences include:

  • String concatenation syntax
  • Comment syntax
  • Stacked or batched queries
  • Platform-specific APIs
  • Error messages

Therefore, understanding the database technology can help when analyzing a SQL Injection vulnerability.

12. Examining the Database

After identifying SQL Injection, information about the underlying database can help determine which techniques are applicable.

For example, database version information can sometimes be queried using database-specific syntax.

Database metadata can also reveal available tables and columns. On many databases, the information_schema contains useful metadata. 

SELECT * FROM information_schema.tables;

13. SQL Injection in Different Request Formats

SQL Injection is not limited to URL query parameters. Any controllable input that eventually reaches an unsafe SQL query may potentially be vulnerable.

Examples include:

  • URL query parameters
  • Form parameters
  • JSON data
  • XML data
  • HTTP headers, where applicable

Different formats can also affect how input is encoded and processed before it reaches the SQL interpreter.

14. Preventing SQL Injection

The primary defense against SQL Injection is to use parameterized queries, also known as prepared statements, instead of directly concatenating user input into SQL statements.

Vulnerable approach

String query =
    "SELECT * FROM products WHERE category = '" + input + "'";

Statement statement =
    connection.createStatement();

ResultSet resultSet =
    statement.executeQuery(query);

Here, the user input becomes part of the SQL statement itself.

Safer approach

PreparedStatement statement =
    connection.prepareStatement(
        "SELECT * FROM products WHERE category = ?"
    );

statement.setString(1, input);

ResultSet resultSet =
    statement.executeQuery();

The ? represents a parameter. The user's input is treated as data rather than being allowed to change the structure of the SQL query.

15. Important Limitation of Parameterized Queries

Parameterized queries are designed for untrusted values within a query. They cannot normally be used to parameterize structural elements such as table names, column names, or an ORDER BY clause.

When these elements must be selected dynamically, applications should use approaches such as:

  • Whitelisting permitted values.
  • Using separate application logic for different allowed options.
