01 — Overview

Challenge overview

An Online Documentation Viewer allowed users to read technical documentation files stored on the server. The application loaded documents based on a URL parameter called doc.

# Example URLs https://challenge.razzify.in/challenge_12/view?doc=api-reference.md https://challenge.razzify.in/challenge_12/view?doc=create-order.md

The objective was to locate and retrieve a hidden file named flag.txt. The challenge description hinted that the file loading mechanism might not properly restrict access to files outside the intended documentation directory.

02 — Recon

Initial reconnaissance

The URL structure immediately revealed that the document being displayed was controlled entirely by the doc parameter. The challenge hints reinforced this:

Hints provided

Observe the URL parameters · The doc parameter may be vulnerable · The flag is stored inside flag.txt

These clues pointed squarely toward a path traversal vulnerability — the backend was reading files from a directory and displaying their contents without sanitizing the input.

03 — Concept

Understanding path traversal

Path traversal occurs when an application accepts file paths from user input without proper validation. Developers typically expect access to files like these:

docs/api-reference.md docs/create-order.md

However, an attacker can use ../ sequences to move up directory levels. The operating system faithfully resolves these, stepping out of the intended directory entirely:

docs/../../flag.txt # traverses up two levels
04 — Exploit

Exploitation process

After identifying the likely vulnerability, the doc parameter was modified to escape the documentation directory using traversal sequences.

# Payload doc=../../flag.txt # Full URL https://challenge.razzify.in/challenge_12/view?doc=../../flag.txt
Result

The application returned the contents of flag.txt, confirming the path traversal vulnerability. No authentication bypass was needed — just a modified URL parameter.

05 — Root cause

Root cause analysis

The vulnerability existed because the application trusted user input when constructing file paths. A simplified version of the vulnerable code would look like this:

doc = request.args.get("doc") open("docs/" + doc) # ← never do this

The application did not validate or sanitize the input, allowing traversal sequences to be interpreted by the OS directly.

06 — Impact

Security impact

In a real-world application, an attacker could access any file the web process has permission to read. Common targets include:

Config files

Source code

API keys & secrets

DB credentials

User data

Server info

# Commonly targeted files /etc/passwd .env web.config application.properties
07 — Remediation

Remediation techniques

01

Input allowlist — Only permit known, explicitly allowed filenames. Reject everything else before touching the filesystem.

02

Canonical path check — Resolve the absolute path with os.path.realpath() and verify it starts with the intended base directory.

03

Strip traversal sequences — Reject inputs containing ../ or ..\ before any path construction.

04

Use file identifiers — Accept an opaque ?id=1 parameter that maps to a predefined file server-side, with no path logic exposed to the user.
