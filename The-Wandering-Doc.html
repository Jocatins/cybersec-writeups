The Wandering Document

Challenge challenge_12 Vulnerability Path Traversal (CWE-22) Platform challenge.razzify.in Category CTF / Web
i Challenge Summary
An online documentation viewer loaded files via a doc URL parameter without sanitizing path traversal sequences, allowing arbitrary file reads outside the intended directory.

This write-up covers the discovery and exploitation of a Path Traversal vulnerability in a web-based documentation viewer. The application served Markdown files from a server directory through a URL parameter — and failed to restrict access to only that directory.

Objective: Locate and read a hidden file named flag.txt on the server.

Initial Reconnaissance

The application served documentation through a doc query parameter in the URL:

Example URLs
https://challenge.razzify.in/challenge_12/view?doc=api-reference.md
https://challenge.razzify.in/challenge_12/view?doc=create-order.md

The direct exposure of a filename in the URL immediately suggested that the backend was constructing a file path from user input — a classic signal for path traversal. The challenge hints confirmed:

  • The doc parameter controls which file is loaded.
  • The parameter may be vulnerable to traversal sequences.
  • The flag is stored in flag.txt at an unknown location above the docs folder.

Understanding Path Traversal

Path Traversal occurs when an application accepts file paths from user input without proper validation. By inserting ../ sequences — which instruct the OS to move up one directory — an attacker can escape the intended directory and access arbitrary files.

Intended path Traversal payload Resolved path
docs/api-reference.md api-reference.md /app/docs/api-reference.md
One level up ../config.json /app/config.json
Two levels up ../../flag.txt /flag.txt
! Why This Works
The operating system resolves ../ at the filesystem level before the application can check what file is being requested. If the app doesn't strip or validate these sequences before constructing the path, the OS does exactly what the attacker intends.

Exploitation

With the vulnerability identified, exploitation was straightforward. The doc parameter was modified to include traversal sequences pointing to flag.txt:

Payload
../../flag.txt
Full Request URL
https://challenge.razzify.in/challenge_12/view?doc=../../flag.txt

The server returned the contents of flag.txt without any error or authentication check, confirming the vulnerability and yielding the flag.

✓ Flag Retrieved
The traversal payload successfully escaped the docs/ directory and read flag.txt from a parent directory. Challenge status: Solved.

Root Cause Analysis

The vulnerability existed because the application concatenated user input directly into a file path with no validation:

Vulnerable Implementation (Python)
doc = request.args.get("doc")
open("docs/" + doc)  # No validation — user controls the full path

A safe version would resolve the full canonical path and verify it remains inside the allowed directory before opening the file:

Secure Implementation (Python)
import os

BASE_DIR = os.path.abspath("docs/")
doc      = request.args.get("doc")
full     = os.path.realpath(os.path.join(BASE_DIR, doc))

if not full.startswith(BASE_DIR + os.sep):
    abort(403)  # Traversal attempt detected

open(full)

Security Impact

In a production environment, this class of vulnerability allows an attacker to read any file the web server process has permission to access:

Configuration files
Application source code
Environment variables
Database credentials
Private API keys
User data / PII
SSH private keys
/etc/passwd (Linux)
! CVSS Classification
Path Traversal is classified as CWE-22 and can achieve CVSS scores of 7.5–9.8 (High to Critical) depending on what files are exposed. It appears consistently in the OWASP Top 10 under Broken Access Control.

Remediation

Four layers of defense can eliminate or mitigate this vulnerability:

Method 01
Canonical Path Check
Resolve the absolute path with os.path.realpath() and assert it starts with the allowed base directory before reading.
Method 02
Allowlist Validation
Only accept filenames that exist in a predefined list. Reject anything else before constructing a path.
Method 03
Strip Traversal Sequences
Reject or sanitize inputs containing ../, ..\, or null bytes before any path construction occurs.
Method 04
Indirect File References
Accept only an opaque ID (e.g. ?id=1) that maps server-side to a specific file, removing path logic from user input entirely.
