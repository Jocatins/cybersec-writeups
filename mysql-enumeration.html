PORTSWIGGER WEB SECURITY ACADEMY

SQL Injection: Database Version Enumeration

A practical investigation into a vulnerable product-category filter, using UNION-based SQL injection to identify the database technology and retrieve its version string.

Difficulty: Practitioner Status: Solved Vulnerability: SQL Injection Technique: UNION Query Database: MySQL

1. Lab Objective

End goal: Display the database version string through the vulnerable product category filter.

The application contains a SQL injection vulnerability in the product category filtering functionality. The objective was to manipulate the backend SQL query and use a UNION attack to retrieve information from the database.

Rather than guessing the database version, I approached the lab as an investigation:

  1. Confirm whether the category parameter is injectable.
  2. Determine the number of columns returned by the original query.
  3. Identify which columns accept text values.
  4. Use a database-specific query to retrieve the version string.

2. Initial Analysis

The vulnerable functionality was the product category filter. The application accepted a category value through the URL: 

/filter?category=Gifts

My first step was to test whether the parameter was being safely handled by the backend. I added a single quote to the parameter: 

'

The application returned an error response, suggesting that the input was reaching a SQL query without being properly parameterised.

Observation: The single quote appeared to interfere with the backend query structure. This was an early indication that the parameter may be vulnerable to SQL injection.

3. Determining the Number of Columns

Before performing a UNION attack, the number of columns in the original query must be known. A UNION query generally requires the injected SELECT statement to return the same number of columns as the original query.

I used the ORDER BY technique to identify the column count. The payloads were tested one at a time in Burp Repeater.

1 Test column 1 
' ORDER BY 1--

This returned an internal server error. I then tested the MySQL comment syntax: 

' ORDER BY 1#

Result: HTTP 200 OK

2 Test column 2 
' ORDER BY 2#

Result: HTTP 200 OK

3 Test column 3 
' ORDER BY 3#

Result: HTTP 500 Internal Server Error

Conclusion

The query accepted column positions 1 and 2 but failed at position 3. This strongly indicated that the original query returned exactly two columns.

Payload Observed Result Interpretation
' ORDER BY 1# 200 OK Column 1 exists
' ORDER BY 2# 200 OK Column 2 exists
' ORDER BY 3# 500 Error Column 3 does not exist

4. Identifying Text-Compatible Columns

After determining that the query contained two columns, I needed to identify which columns could display text.

I used a UNION query that returned the same number of columns and placed a simple text marker in both positions: 

' UNION SELECT 'a', 'a'#

The request returned HTTP 200 OK. In the Burp response, the injected text was visible in the page output: 

<th>a</th>
<td>a</td>
Finding: Both columns accepted text values and were reflected in the application response. This confirmed that the UNION query was being executed successfully.

5. Extracting the Database Version

With the column count and text-compatible positions confirmed, I replaced the test marker with a database version query.

The payload used was:

' UNION SELECT @@version, NULL#

The query returned the database version in the first column while using NULL for the second column to preserve the required two-column structure.

Observed Version

8.0.42-0ubuntu0.20.04.1
Lab solved: The database version string was successfully displayed.

6. Database Identification

The returned version string indicates that the target database was MySQL running on Ubuntu: 

8.0.42-0ubuntu0.20.04.1
  • Database technology: MySQL
  • Major version: 8.0
  • Operating-system packaging: Ubuntu package build
  • Information source: @@version
Important clarification: The # symbol is a MySQL comment marker. It does not mean that the database is Microsoft SQL Server. The returned version string confirms MySQL.

7. Technical Reasoning

The original application likely constructed a query similar to:

SELECT product_name, product_description
FROM products
WHERE category = 'Gifts';

By injecting a quote, the original string context was closed. The UNION statement then added a second SELECT query to the original query.

Conceptually, the injected query became similar to:

SELECT product_name, product_description
FROM products
WHERE category = ''
UNION
SELECT @@version, NULL#';

The final comment marker caused the remaining part of the original query to be ignored by MySQL.

Why the UNION query worked

  • The original query returned two columns.
  • The injected query also returned two columns.
  • The first column accepted and displayed text.
  • The second column was satisfied with NULL.
  • The application reflected the first column in the response.

8. Lessons Learned

  1. Start with confirmation: A single quote can reveal whether input is affecting SQL syntax.
  2. Column enumeration is essential: UNION attacks require the injected SELECT statement to match the original column count.
  3. HTTP status codes provide useful clues: A successful response does not always prove the payload worked, but changes between 200 and 500 responses can help identify query boundaries.
  4. Response content is important: The appearance of the marker a confirmed that the injected UNION query was reflected in the page.
  5. Database-specific syntax matters: MySQL uses # for comments, while other database systems may require different syntax.
  6. Understand the reason behind each payload: The goal is not to memorise strings, but to understand how the payload changes the backend query.

9. Recommended Remediation

The vulnerability should be fixed by preventing user-controlled input from being directly concatenated into SQL queries.

Use parameterised queries

SELECT product_name, product_description
FROM products
WHERE category = ?;

Additional protections

  • Use prepared statements or a safe ORM query API.
  • Validate category values against an allowlist.
  • Use a database account with minimum required privileges.
  • Avoid exposing detailed database errors to users.
  • Implement secure error handling and monitoring.
  • Perform security testing on all user-controlled parameters.

10. Final Summary

This lab demonstrated how a vulnerable product-category filter could be exploited using UNION-based SQL injection. I confirmed the injection, identified that the original query returned two columns, verified that both columns accepted text, and finally retrieved the database version using the MySQL @@version variable.

Final result:

The target database was identified as MySQL, and the version string displayed was:

8.0.42-0ubuntu0.20.04.1
