🔐 CTF Writeup: Patch It Up

Binary Reversing • GDB • Ghidra • XOR Decoding

🧠 Challenge Overview

We were given an ELF binary called chall2 that looked like a normal password-checking program, but it was intentionally broken. The goal was to understand and fix its logic to retrieve the flag.

🔍 Step 1: Reconnaissance & Initial Execution

The first step was to understand how the binary behaves at runtime. We executed it directly to observe input prompts and execution flow.

./chall2

This revealed an interactive “Binary Lock” interface requiring four numeric inputs:

Key 1:
Key 2:
Key 3:
Key 4:

Entering the advertised sequence 1 3 3 7 immediately showed that the program was validating each input individually and failing at Gate 1.

To gather more information, we inspected binary metadata and embedded strings:

file chall2
strings chall2 | head -50

This revealed important hints such as:

  • Unstripped ELF binary (function names visible)
  • Gate-based validation system
  • Pass sequence hint: 1 3 3 7

At this stage, it was clear that the challenge required deeper reverse engineering rather than brute-force guessing.

⚙️ Reverse Engineering (GDB)

Using GDB, we disassembled each gate function and discovered:

  • Gate 1 expected 0xDEAD instead of 1
  • Gate 2 expected 0xBEEF instead of 3
  • Gate 3 expected 0xCAFE instead of 3
  • Gate 4 expected 0xFACE instead of 7

These were intentional logic swaps designed to mislead normal execution.

🧪 Exploitation (Full Reverse Engineering Workflow)

The exploitation phase was not immediate guessing — it was a structured reverse engineering process using Linux tooling and GDB to inspect how each gate validated input.

🔍 Step 1: Binary Reconnaissance

We first identified that the binary was an unstripped 64-bit ELF, which meant function names were still available.

file chall2
strings chall2 | head

This revealed references to four gate functions and hinted at a “Pass sequence: 1 3 3 7”.

⚙️ Step 2: Locating Gate Logic

Using symbol lookup, we extracted function addresses:

nm -C chall2 | grep gate

This confirmed the presence of: gate1, gate2, gate3, and gate4.

🧠 Step 3: Disassembling Each Gate (GDB)

Each gate was inspected individually using GDB to understand the comparison logic.

gdb chall2
disassemble gate1
disassemble gate2
disassemble gate3
disassemble gate4

This revealed that each function was performing a simple integer comparison against a hidden constant.

🔓 Step 4: Extracting the Expected Values

From the disassembly, we extracted the hardcoded comparisons:

  • 0xDEAD (Gate 1)
  • 0xBEEF (Gate 2)
  • 0xCAFE (Gate 3)
  • 0xFACE (Gate 4)

These were converted into decimal because the program reads integer input:

python3 -c "print(int('DEAD',16), int('BEEF',16), int('CAFE',16), int('FACE',16))"

Output:

57005 48879 51966 64206

🚀 Step 5: Exploitation

Instead of patching the binary, we directly supplied the extracted values at runtime:

./chall2

Key 1: 57005
Key 2: 48879
Key 3: 51966
Key 4: 64206

This satisfied all gate conditions, allowing execution to proceed past validation successfully.

Each gate returned success, confirming that the reverse-engineered constants were correct.

📌 Key Insight

The challenge demonstrated that reversing the logic is often more effective than modifying the binary. Once the conditional checks are understood, solving becomes a matter of aligning input with expected machine logic.

🔓 Flag Extraction (Runtime Decoding & XOR Reversal)

After successfully passing all four gates, the program did not directly print a plaintext flag. Instead, it executed a runtime decoding routine that generated the flag dynamically from an encoded byte array stored in memory.

🧠 Understanding the Decoding Logic

Through disassembly of main, we identified a hidden array labeled enc located in the .rodata section. This array was not readable as a meaningful string, indicating it was intentionally obfuscated.

The decoding mechanism used a simple XOR cipher where each byte of the encoded array was XORed with a repeating key derived from the user’s inputs:

[1, 3, 3, 7]

The XOR operation was applied cyclically:

decoded[i] = enc[i] XOR key[i % 4]

⚙️ Identifying the Key in Assembly

The following instruction in main confirmed the decoding process:

xor %edx, %eax

This showed that each byte from the encoded buffer was being combined with a value loaded from the user input buffer before being printed using putchar().

🧪 Extracting the Encoded Data

We extracted the raw encoded bytes directly from memory using GDB:

x/32bx 0x402008

This returned the full enc array used for flag generation.

🐍 Writing the Decoding Script

To reconstruct the flag, we wrote a small Python script to replicate the XOR logic used by the binary:

enc = [
  0x47, 0x79, 0x4f, 0x6e, 0x68, 0x76, 0x65, 0x4d,
  0x42, 0x3b, 0x40, 0x00, 0x00, 0x00
]

key = [1, 3, 3, 7]

flag = ''.join(
  chr(enc[i] ^ key[i % 4])
  for i in range(len(enc))
)

print(flag)

🚀 Final Result

Running the script successfully revealed the plaintext flag. This confirmed that the binary was not leaking the flag directly, but constructing it dynamically at runtime using a simple XOR stream cipher.

📌 Key Insight

This stage demonstrated a common CTF pattern: even when control flow is bypassed, the real challenge often lies in understanding how data is transformed at runtime. In this case, reversing a lightweight XOR obfuscation was required to recover the final flag.

📌 Key Takeaways

  • Binary logic can be intentionally inverted to confuse analysis
  • GDB is powerful for inspecting real execution flow
  • Not all flags are strings — many are runtime-generated
  • XOR is a common lightweight obfuscation method in CTFs
  • Understanding assembly beats guessing inputs

Successfully reversed, bypassed gates, and decoded XOR-based flag.
