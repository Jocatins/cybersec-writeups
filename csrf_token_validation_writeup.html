🏴 CSRF Token Validation - CTF Writeup

Flag Captured: zJE3PN^l$XO

This challenge focused on identifying a flaw in how a web application validated CSRF tokens. The application appeared secure at first because requests without a CSRF token were rejected, but deeper testing revealed a parameter pollution vulnerability.

🎯 Objective

Change the notification email address and exploit the CSRF validation weakness to obtain the secret flag.

🔎 Reconnaissance

  • Visited the Employee Portal account page.
  • Observed that only email addresses ending with @victim.com were accepted.
  • Captured the request using browser developer tools.
POST /challenge_45/email/change

email=nicodaemon05@victim.com
csrf_token=741f3f8980efcc953ea677ee7fb1b424

🛠 Moving to Burp Suite

The challenge required manipulating requests, making Burp Suite the ideal tool.

  • Configured Firefox to proxy traffic through Burp.
  • Intercepted the email change request.
  • Sent the request to Repeater for experimentation.

🧪 Testing the CSRF Validation

Test 1: Remove the token

email=nicodaemon05@victim.com

Result: 400 - CSRF token missing or invalid

Test 2: Use a fake token

email=nicodaemon05@victim.com
csrf_token=abc

Result: 400 - CSRF token missing or invalid

Test 3: Duplicate CSRF parameters

email=nicodaemon05@victim.com
csrf_token=741f3f8980efcc953ea677ee7fb1b424
csrf_token=abc

Result: 302 Redirect

This indicated a parameter pollution issue where one component validated the first token while another processed the second token.

🚩 Obtaining the Flag

After enabling Follow Redirections in Burp Repeater, the redirected response contained the flag:

zJE3PN^l$XO

🌍 Real-World Relevance

  • Demonstrates why applications must reject duplicate security parameters.
  • Shows the dangers of inconsistent request parsing between frameworks and middleware.
  • Highlights the importance of testing beyond simple valid/invalid scenarios.
  • Reinforces the value of intercepting proxies during web application assessments.
