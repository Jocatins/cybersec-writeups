Reflected XSS into a JavaScript String with Angle Brackets HTML Encoded

A practical walkthrough of identifying a JavaScript string injection vulnerability, analyzing reflection in Burp Suite, understanding JavaScript function calls, and constructing a working XSS payload.

Difficulty: Apprentice

1. Lab Overview

This lab demonstrates a reflected Cross-Site Scripting (XSS) vulnerability in a blog's search functionality.

The application reflects the user's search input inside a JavaScript string used by the search tracking functionality. Although angle brackets are HTML encoded, the application does not safely handle the JavaScript string context.

Core vulnerability: User-controlled input is inserted into a JavaScript string without safely preventing the input from breaking out of that string.

2. Lab Objective

The objective is to perform a reflected XSS attack that breaks out of the JavaScript string containing the search term and executes the JavaScript alert function.

The successful proof of concept is a browser alert popup.

Success condition: The browser executes the injected JavaScript and displays an alert popup when the lab page is loaded with the crafted search query.

3. Initial Investigation and Reconnaissance

I started by interacting with the lab's search functionality. The goal was to understand how the application handled and reflected user input.

3.1 Submit a normal search term

I entered a random alphanumeric value into the search box. For example: 

Nicholas123

The server returned a page containing the search term in the page's search results and tracking functionality.

3.2 Intercept the request with Burp Suite

I used Burp Suite to observe the HTTP request generated by the search form and sent the request to Burp Repeater for further testing.

The relevant request parameter was: 

search=Nicholas123

The exact request path and other HTTP headers may vary depending on the lab session.

3.3 Observe where the input is reflected

The response reflected my input inside a JavaScript variable. This was the important discovery because the input was not only being displayed as ordinary HTML text. 

<script>
    var searchTerms = 'Nicholas123';
</script>
Key observation: The input is inside single quotes in a JavaScript string. This changes the way the payload must be constructed.

4. Testing Angle Brackets and Understanding HTML Encoding

During my initial troubleshooting, I experimented with angle brackets because XSS is commonly associated with HTML elements such as <script> or event-handler attributes.

However, the application returned angle brackets in encoded form. This indicated that the application was applying HTML encoding to those characters.

4.1 Example of HTML encoding

Character Encoded representation
< &lt;
> &gt;
& &amp;
" &quot; in common HTML contexts
' &#39; in common HTML contexts

4.2 Why this mattered

The angle brackets being encoded suggested that an HTML-tag-based payload might not work in this location.

Instead of continuing to focus only on HTML tags, I inspected the JavaScript context where the input was reflected.

Important lesson: HTML encoding does not automatically make JavaScript string interpolation safe. The correct analysis depends on the context where the input is inserted.

5. Identifying the Vulnerable JavaScript

The relevant part of the response was: 

<script>
    var searchTerms = 'USER_INPUT';

    document.write(
        '<img src="/resources/images/tracker.gif?searchTerms='
        + encodeURIComponent(searchTerms)
        + '">'
    );
</script>

In this example, USER_INPUT represents the value supplied through the search parameter.

5.1 Normal input

If the input is: 

hello

The resulting JavaScript is: 

var searchTerms = 'hello';

This is valid JavaScript. The search term is simply a string assigned to the variable.

5.2 The vulnerable location

The application places the user's input between the opening and closing single quotes: 

var searchTerms = 'USER_INPUT';

Therefore, a single quote in the input can potentially interfere with the string boundary.

Injection context: JavaScript string delimited by single quotes.

6. Understanding alert(), alert(1), and alert("Nicholas")

One of the main things I learned from this lab was that alert(1) is not a special XSS function. It is simply a normal JavaScript function call.

6.1 What is alert()?

alert is a browser-provided JavaScript function that displays a message in a dialog box. 

alert();

This calls the function without providing a message.

6.2 What is alert(1)?

alert(1);

The value inside the parentheses is called an argument. In this case, the argument is the number 1.

The function displays the number as the alert message.

6.3 What is alert("Nicholas")?

alert("Nicholas");

Here, the argument is the string "Nicholas". The alert dialog displays that text.

Expression Explanation
alert() Call alert without an argument.
alert(1) Call alert with the number 1.
alert("Nicholas") Call alert with the text Nicholas.
alert("XSS") Call alert with the text XSS.
Key takeaway: The number 1 is only the alert message. The XSS vulnerability comes from getting JavaScript code to execute in an unintended location.

7. Constructing the Payload

After identifying the JavaScript string context, I experimented with a payload that could break out of the string and execute JavaScript.

7.1 The successful payload

'-alert(1)-'

The payload consists of:

7.2 Payload with a custom alert message

During browser experimentation, I also observed that the following variation executed successfully:

'-alert("Nicholas")-'

This works for the same reason as the original lab payload: the alert function is evaluated as JavaScript code rather than remaining inside the original string.

Lab result: Both the original solution using alert(1) and the variation using alert("Nicholas") successfully demonstrated JavaScript execution in the lab.

8. Breaking Down '-alert(1)-'

The most important part of this lab is understanding why the payload is structured this way.

8.1 The original JavaScript

var searchTerms = 'USER_INPUT';

The application expects the search term to be a string.

8.2 After injecting the payload

When the payload is reflected, the JavaScript becomes: 

var searchTerms = ''-alert(1)-'';

The two adjacent single quotes at the beginning and end are important. They are not simply decorative characters.

8.3 First single quote: close the original string

The first single quote in the payload closes the string that the application originally opened. 

var searchTerms = ''

At this point, the original string is closed.

8.4 The minus operator

The minus sign is the JavaScript subtraction operator. It allows the injected content to form part of an expression. 

-alert(1)-

JavaScript evaluates the function call while evaluating the expression.

8.5 alert(1): the function call

alert(1)

This is the actual JavaScript function call that produces the browser alert.

8.6 Final single quote: complete the expression

The final single quote begins another string, which allows the expression to fit into the surrounding JavaScript. 

''

8.7 Complete breakdown

Original string closes
'
↓
JavaScript expression
-alert(1)-
↓
New string begins
'
↓
Browser evaluates the alert call
Precision: The minus signs are not required because alert is an XSS-specific function. They help construct a JavaScript expression that fits the surrounding syntax in this lab.

9. Why Not Simply Use 'alert(1)'?

A natural first attempt might be: 

'alert(1)'

When reflected into the vulnerable code, this becomes: 

var searchTerms = ''alert(1)'';

This is not valid JavaScript syntax.

The string closes, but the remaining characters do not form a valid expression in the surrounding code.

9.1 The role of the minus operators

The working payload is: 

'-alert(1)-'

It becomes: 

var searchTerms = ''-alert(1)-'';

The subtraction operators make the injected function call part of a valid expression structure.

The key is not simply "insert alert". The key is to construct JavaScript syntax that works with the code surrounding the reflection point.

12. Why the XSS Works

The vulnerability exists because the application reflects user-controlled input into JavaScript without correctly handling the JavaScript string boundary.

12.1 Expected behavior

var searchTerms = 'hello';

The input is treated as data.

12.2 Vulnerable behavior

var searchTerms = ''-alert(1)-'';

The input changes the structure of the JavaScript expression. The browser parses the injected function call as code.

12.3 The vulnerability is reflected XSS

The malicious input is supplied through an HTTP request and reflected into the response. It is not stored permanently by the application as part of the lab's attack.

Reflected XSS: Malicious input is reflected by the server into a page and executed by the victim's browser when the vulnerable page is loaded.

13. Understanding the Tracking Function

The lab includes the following tracking code: 

document.write(
    '<img src="/resources/images/tracker.gif?searchTerms='
    + encodeURIComponent(searchTerms)
    + '">'
);

This code creates an image element whose URL contains the search term.

13.1 What encodeURIComponent does

encodeURIComponent() encodes a value for use as part of a URL component. 

encodeURIComponent("hello world")

Produces a URL-encoded representation such as: 

hello%20world

13.2 Why it does not fix the original vulnerability

The tracking URL encoding happens after the value has already been assigned to the JavaScript variable. 

var searchTerms = 'USER_INPUT';

encodeURIComponent(searchTerms);

The dangerous operation is the initial insertion of the input into the JavaScript string. Encoding the value later for a URL does not retroactively make that earlier JavaScript assignment safe.

Context matters: URL encoding, HTML encoding, and JavaScript string escaping are different operations. Encoding for one context does not necessarily protect another context.

14. Troubleshooting and Failed Attempts

During the lab, I initially experimented with angle brackets and HTML-based payloads. They were not effective in the relevant JavaScript string context.

14.1 Angle bracket payloads

Example: 

<script>alert(1)</script>

The application encoded angle brackets, so the input was not interpreted as an HTML script element.

14.2 Simple quote payload

Example: 

'alert(1)'

This did not produce valid JavaScript in the lab's surrounding expression.

14.3 Successful payload

'-alert(1)-'

The successful payload closes the original string and places the function call inside a JavaScript expression.

What I learned from the failed attempts: A payload must be designed for the exact context in which the application reflects the input. A generic XSS payload may fail even when a vulnerability exists.

15. A General XSS Context Identification Method

This lab helped me develop a more structured approach to identifying reflected XSS vulnerabilities.

  1. Submit a unique marker.

    Use a random string so you can locate your input in the response.

  2. Inspect the response.

    Find exactly where the marker appears.

  3. Identify the context.

    Determine whether the input is inside HTML text, an HTML attribute, JavaScript, CSS, or another context.

  4. Identify the delimiters.

    For JavaScript strings, inspect the opening and closing quotes.

  5. Understand the surrounding syntax.

    Look at the code immediately before and after the reflection point.

  6. Construct a context-appropriate proof of concept.

    Use a harmless alert in the authorized lab environment to confirm execution.

  7. Verify execution in the browser.

    A reflected payload in the HTTP response is not enough by itself; confirm whether the browser executes it.

18. How Developers Can Prevent This Vulnerability

The correct defense is to prevent untrusted input from being interpreted as JavaScript code.

18.1 Avoid placing untrusted input directly inside JavaScript

Vulnerable pattern: 

var searchTerms = 'USER_INPUT';

A safer approach is to keep user input in a data context rather than generating JavaScript source code from it.

18.2 Use context-appropriate escaping

If data must be inserted into a JavaScript string, use a reliable JavaScript-aware serialization or escaping mechanism appropriate for the exact context.

18.3 Prefer safe DOM APIs

Avoid constructing HTML with untrusted values when possible. Use safe DOM APIs and treat user-controlled data as data.

18.4 Use Content Security Policy

A properly designed Content Security Policy can reduce the impact of some XSS vulnerabilities. However, it should not be treated as a replacement for safe input handling and output encoding.

Developer takeaway: The application should prevent untrusted input from changing JavaScript syntax, not merely encode HTML characters.

19. Final Summary

This lab demonstrated a reflected XSS vulnerability caused by inserting user-controlled search input into a JavaScript string.

My initial troubleshooting involved testing angle brackets, which were returned in encoded form. By using Burp Suite to inspect the response, I identified that the search input was reflected inside a JavaScript variable.

I then experimented with JavaScript syntax and discovered that the payload:

'-alert("Nicholas")-'

executed successfully in the lab and triggered a browser alert. The official lab payload using alert(1) also worked.

The most important lesson was that XSS payloads must be constructed according to the injection context. In this case, the vulnerability was inside a JavaScript string, so the key was understanding string boundaries and JavaScript expressions.
